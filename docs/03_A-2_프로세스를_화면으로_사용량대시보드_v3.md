### 0-b. 주요 내부 로직 (각 1줄)

- **인증 도메인 화이트리스트**: `ALLOWED_EMAIL_DOMAINS` (쉼표 구분) 미일치 → `/login?error=domain`. 빈 값이면 모든 도메인 허용.
- **어드민 판정**: `ADMIN_EMAIL` 환경변수 (쉼표 구분). 어드민만 `/member` + `/team/[userId]/dashboard` + 팀 페이지 Last Sync/Top Sessions 카드 노출.
- **API 키 발급**: CLI 가 OAuth 후 `/api/cli-auth?port=9988` 호출 → 32바이트 hex 신규 발급 + sha256 해시 DB 저장 → `127.0.0.1:9988/?apiKey=...` 리다이렉트로 CLI 에 전달.
- **데이터 수집 스케줄**: macOS launchd `StartInterval` 7200초 (2시간), sleep 시 카운트다운 정지 → wake 즉시 1회 fire. Windows Task Scheduler 0/6/12/18 + `StartWhenAvailable=true`.
- **수집 페이로드**: codeburn report x5 (today/week/month/30days/all) + ccusage daily, `Promise.allSettled` 600초 timeout → POST `/api/ingest` (X-API-Key).
- **ccusage 머지**: `body.ccusageDaily` 비었거나 missing 인데 prev 에 데이터 있으면 prev 의 ccusageDaily 보존 (1회 timeout 으로 토큰 wipe 차단).
- **Boundary 감지**: `today.period` 라벨 (`Today (YYYY-MM-DD)`) 정규식으로 사용자 로컬 today 추출 → 월요일/1일 boundary 계산. timezone NULL 이어도 동작.
- **Snapshot 승격**: `currentDayStart/WeekStart/MonthStart` 가 prev 와 다르면 prev rawJson 을 `period_snapshots` 에 INSERT (daily/weekly/monthly).
- **Retention**: weekly 5주, monthly 12달, daily 7일 보다 오래된 period_snapshots 삭제.
- **Period 필터**: `today / month / 8days / 30days / all` 5개. legacy `week` localStorage 값은 `8days` 로 자동 마이그레이션.
- **Heatmap 길이 적응형**: `clamp(ceil(데이터일수/7), min=15, max=26)` 주. UI 라벨도 동적 (예: "활동 히트맵 (16주, 비용 기준)").
- **효율 등급**: 6개 메트릭 (cache/one-shot/cost-per-session/calls-per-session/cost-per-call/output-input ratio) 각각 5단계 (탁월/양호/보통/부족/경고) → 종합 등급은 cache×0.4 + 1shot×0.4 + cost×0.2 가중치.
- **stale 멤버 필터** (팀 페이지): 멤버 `rawJson.{month,today}.daily[0].date` 가 현재 UTC YYYY-MM(-DD) 와 다르면 0 처리 + 활동 합산에서 제외.
- **DashboardView 자동 분기**: `!user.lastSyncedAt && !viewOnly` 면 `/setup` 으로 redirect. `!overview` 면 sync 명령 화면 표시.
- **Setup-status fetch 실패 처리** (v3 신규): HTTP not-ok 또는 reject 시 `fetchError=true` → 에러 메시지 + [다시 시도] 버튼 → 클릭하면 reloadKey 증가 + useEffect 재실행.
- **CLI ownership preflight**: install.sh 가 `~/.npm` + `~/.primus-usage-tracker` + `~/.primus-usage-key` + LaunchAgent plist 4 위치 모두 root 소유 검사 → 한 번에 chown 명령 출력. `.pkg` Node 감지 시 nvm 전환 권유.

## §1. A-1 요약 블록

**A-0 핵심 가설**
Primus Labs 개발자 10명이 Claude Code 세션마다 자동 수집된 사용량 데이터를 개인 대시보드 + 팀 랭킹으로 확인하면서 (1) 자기 워크플로우를 최적화하고 (2) 가벼운 경쟁을 즐길 것이다. **lower bar: 본인이 한 달에 한 번 보면 성공.**

**MVP 경계 3개**
- 제품: Claude Code 사용량 자동 수집 + 사내 웹 대시보드 (Codex/Gemini 제외)
- 타겟: Primus Labs 사내 개발자 10명 안팎
- 목표 행동: 주 1회 대시보드 방문 + 월 1회 자기 통계 보고 워크플로우 변경

**Phase 구조 (코드 검증)**
- P0. 온보딩 & 셋업 (/login → /setup → /dashboard)
- P1. 자동 수집 (UI 없음, launchd/Task Scheduler)
- P2. 조회 — 개인 + 팀 (/dashboard ↔ /team ↔ /team/[userId] ↔ /setup-status)
- P3. (어드민) 팀원 진단 (/member ↔ /team/[userId]/dashboard)

**기술 스택 (코드 검증)**
- 프레임워크: Next.js 14 App Router (web + API 단일 코드베이스)
- DB: Postgres 본번/Supabase, Drizzle ORM
- 인증: NextAuth.js (GitHub + Google), 도메인 화이트리스트 + ADMIN_EMAIL
- UI: Tailwind + Recharts (AreaChart) + react-activity-calendar (heatmap)
- CLI: Bun + commander, npm 글로벌 ccusage + codeburn 의존
- 데이터 수집: launchd (`StartInterval 7200s`) / Windows Task Scheduler. SessionEnd hook 미사용 (코드에서 removeHook 으로 제거).
- 비밀 저장: keytar (Mac Keychain / Win Cred / Linux libsecret) + `~/.primus-usage-key` 파일 fallback
- 차트: 자체 막대 (CSS bar) + Recharts AreaChart (팀 By Member/Total) + ActivityCalendar (heatmap)

### 화면 #1 — `/login`

#### 4-a. Wireframe

```
┌──────────────────────────────────────────────┐
│                                              │
│           Primus Usage Tracker               │  ← h1
│      AI 코딩 도구를 얼마나, 어떻게            │  ← 1줄 설명
│         쓰고 있는지 한눈에                    │
│            팀 멤버 전용                       │  ← 작은 보조
│                                              │
│  ┌──────────────────────────┐                │
│  │ ⓖ  GitHub로 시작하기      │                │
│  └──────────────────────────┘                │
│  ┌──────────────────────────┐                │
│  │ G   Google로 시작하기     │                │
│  └──────────────────────────┘                │
│                                              │
│  ?error=domain 인 경우:                       │
│  ┌──────────────────────────────┐            │
│  │ 허용되지 않은 이메일 도메인입│            │  ← 빨간 배지
│  │ 니다.                        │            │
│  └──────────────────────────────┘            │
```

#### 4-b. UX 의도

- **2개 OAuth 동등 노출**: 회사 GitHub / Google 모두 정식. 한쪽이 안 되는 멤버를 위한 fallback.
- **회사 도메인 화이트리스트는 OAuth 콜백 후 검증**: 사용자가 OAuth 끝낸 다음에야 거부. 사전 안내는 "팀 멤버 전용" 한 줄.
- **에러 inline**: 별도 페이지 없이 빨간 배지로 즉시 재시도 가능.

#### 4-c. 인터랙션

## 적대적 압박 — Kill 할 이유 3개

A-2 v3 단계의 Kill 이유는 **수렴 후 남아 있는 미세 UX 결함**.

1. **/team 의 어드민 vs 일반 정보 격차가 여전히 노출 형태로**:
   - 일반 사용자 화면: 7개 카드 (Activity/Cost/Efficiency/TeamActivities/Tools/Shell/By Model)
   - 어드민 화면: 위 7개 + Last Sync + Top Sessions = 9개
   - "어드민만 보는 카드 2개" 가 Row 6 으로 뒤에 박혀 있어 일반 사용자가 어드민에게 "그 자료 보여달라" 요청 가능성. v2 의 본 항목 결정 (V2-2 와 별개로 Last Sync 일반 노출 여부) 은 "필요 없음" 으로 답해졌으나, 일반 사용자가 본인 last sync 외에 **다른 멤버의 last sync** 까지 알아야 협업 (예: "X 가 며칠 안 보임" 자가 인지) 가능한 시나리오는 수면 아래.
   - 우선순위 낮음 — 운영 데이터 더 보고 결정.

2. **stale 멤버 0 처리 + SyncBadge 의 시각 모순**:
   - 서버에서 stale 멤버를 totalCost=0 처리 (period=today/month) + 활동 합산 제외
   - UI 에선 SyncBadge 로 "5일 전 sync" 표시 + Efficiency 표 0 값으로 등장
   - "이 사람 0 인데 왜 표시?" 인지 부담
   - 옵션: stale 멤버 행 숨김 vs "—" 명시. 현재는 옵션 0 (어떤 처리도 안 함).
   - Kill 후보지만 큰 결함 아님 (어드민 1명만 봄).

3. **/team/[userId] 와 /setup-status 의 fetch 실패 처리 비대칭**:
   - /setup-status 는 v3 에서 [다시 시도] 버튼 추가
   - /team/[userId], /dashboard/[?] (/team/[userId]/dashboard 는 DashboardView 라 처리됨), /dashboard/detail (제거됨) 등 다른 페이지의 fetch 실패는 미처리
   - 사용자가 /team/[userId] 에서 fetch 실패하면 "로딩 중..." 영원히
   - V2-3 의 정신 ("silent fail 차단") 을 다른 페이지에도 일관 적용해야 함
   - v3.1 에서 다룰 만한 백로그.

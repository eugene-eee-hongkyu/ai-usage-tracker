### 0-b. 주요 내부 로직 (각 1줄)

- **인증 도메인 화이트리스트**: `ALLOWED_EMAIL_DOMAINS` (쉼표 구분) 미일치 → `/login?error=domain`. 빈 값이면 모든 도메인 허용.
- **어드민 판정**: `ADMIN_EMAIL` 환경변수 (쉼표 구분). 어드민만 `/member` + `/team/[userId]/dashboard` + 팀 페이지 Last Sync/Top Sessions 카드 노출.
- **API 키 발급**: CLI 가 OAuth 후 `/api/cli-auth?port=9988` 호출 → 32바이트 hex 신규 발급 + sha256 해시 DB 저장 → `127.0.0.1:9988/?apiKey=...` 리다이렉트로 CLI 에 전달.
- **데이터 수집 스케줄**: macOS launchd `StartInterval` 7200초 (2시간), sleep 시 카운트다운 정지 → wake 즉시 1회 fire. Windows Task Scheduler 0/6/12/18 + `StartWhenAvailable=true`.
- **수집 페이로드**: codeburn report x5 (today/week/month/30days/all) + ccusage daily, `Promise.allSettled` 600초 timeout → POST `/api/ingest` (X-API-Key).
- **ccusage 머지**: `body.ccusageDaily` 비었거나 missing 인데 prev 에 데이터 있으면 prev 의 ccusageDaily 보존.
- **Boundary 감지**: `today.period` 라벨 (`Today (YYYY-MM-DD)`) 정규식으로 사용자 로컬 today 추출 → 월요일/1일 boundary 계산. timezone NULL 이어도 동작.
- **Snapshot 승격**: `currentDayStart/WeekStart/MonthStart` 가 prev 와 다르면 prev rawJson 을 `period_snapshots` 에 INSERT.
- **Retention**: weekly 5주, monthly 12달, daily 7일 보다 오래된 period_snapshots 삭제.
- **Period 필터**: `today / month / 8days / 30days / all` 5개. legacy `week` localStorage 값은 `8days` 로 자동 마이그레이션.
- **Heatmap 길이 적응형**: `clamp(ceil(데이터일수/7), min=15, max=26)` 주. UI 라벨도 동적.
- **효율 등급**: 6개 메트릭 각각 5단계 → 종합 등급 = cache×0.4 + 1shot×0.4 + cost×0.2.
- **stale 멤버 필터** (팀 페이지): 멤버 `rawJson.{month,today}.daily[0].date` 가 현재 UTC YYYY-MM(-DD) 와 다르면 0 처리 + 활동 합산 제외.
- **DashboardView 자동 분기**: `!user.lastSyncedAt && !viewOnly` 면 `/setup` redirect. `!overview` 면 sync 명령 화면 표시.
- **Setup-status fetch 실패 처리**: HTTP not-ok 또는 reject 시 에러 화면 + [다시 시도] 버튼 → reloadKey 증가로 useEffect 재실행.
- **Visit 카운트 (v4 신규)**: DashboardView mount-time 에 1회 `POST /api/visit` → `daily_visits (user_id, date)` 행에 `count + 1` atomic upsert. session.user 만 카운트 (어드민이 viewOnly 로 다른 사람 봐도 어드민 본인 row 에 +1). period/offset 변경엔 재호출 안 됨. today 는 `users.timezone` (NULL → UTC) 기준.
- **Visit heatmap (v4 신규)**: `/api/dashboard` 응답의 `visitDaily` 배열 (15~26주 적응형, activity heatmap 과 동일 로직). DashboardView Row 6 우측 placeholder 자리에 amber 카드. 5단계 (0/1/2-3/4-5/6+).
- **CLI ownership preflight**: install.sh 가 `~/.npm` + `~/.primus-usage-tracker` + `~/.primus-usage-key` + LaunchAgent plist 4 위치 모두 root 소유 검사 → 한 번에 chown 명령 출력. `.pkg` Node 감지 시 nvm 전환 권유.

## §1. A-1 요약 블록

**A-0 핵심 가설**
Primus Labs 개발자 10명이 Claude Code 세션마다 자동 수집된 사용량 데이터를 개인 대시보드 + 팀 랭킹으로 확인하면서 (1) 자기 워크플로우를 최적화하고 (2) 가벼운 경쟁을 즐길 것이다. **lower bar: 본인이 한 달에 한 번 보면 성공.**

**MVP 경계 3개**
- 제품: Claude Code 사용량 자동 수집 + 사내 웹 대시보드
- 타겟: Primus Labs 사내 개발자 10명 안팎
- 목표 행동: 주 1회 대시보드 방문 + 월 1회 자기 통계 보고 워크플로우 변경

**Phase 구조 (코드 검증)**
- P0. 온보딩 & 셋업 (/login → /setup → /dashboard)
- P1. 자동 수집 (UI 없음, launchd/Task Scheduler)
- P2. 조회 — 개인 + 팀 (/dashboard ↔ /team ↔ /team/[userId] ↔ /setup-status)
- P3. (어드민) 팀원 진단 (/member ↔ /team/[userId]/dashboard)

**기술 스택 (코드 검증)**
- 프레임워크: Next.js 14 App Router
- DB: Postgres / Supabase, Drizzle ORM. **신규 테이블 `daily_visits`** (v4)
- 인증: NextAuth.js (GitHub + Google), 도메인 화이트리스트 + ADMIN_EMAIL
- UI: Tailwind + Recharts (AreaChart) + react-activity-calendar
- CLI: Bun + commander, npm ccusage + codeburn 의존
- 데이터 수집: launchd / Windows Task Scheduler. SessionEnd hook 미사용
- 비밀 저장: keytar + `~/.primus-usage-key` 파일 fallback

#### 4-b. UX 의도

- **Period 5탭, Overview Bar, 6 row 카드** — v3 §4 화면 #3 의도 그대로 유지.
- **Visit heatmap (★ v4 신규)**:
  - **lower bar 가설 ("한 달에 한 번 보면 성공") 의 직접 측정**: 본인이 자기 데이터 며칠 봤는지를 본인이 시각으로 확인. activity heatmap 옆에 비슷한 시각으로 두어 "한 칸이 작업, 옆에 한 칸이 봐줌" 짝.
  - **본인 동기 부여**: "이번주 3번 봤네" 는 자기 강화. monthly 페이지 갱신 안 해도 "벌써 12일 연속 봤어" 같은 streak 느낌 자연 발생.
  - **어드민 engagement 진단**: 어드민이 viewOnly 모드로 멤버 dashboard 보면 그 멤버의 visit count 가 보임. 셋업만 하고 한 번도 안 본 멤버를 한눈에 발견 ("도구 가치 부족" 신호 → 알림 주기).
  - **5단계 색 (amber 0/1/2-3/4-5/6+)**: 일별 1회 = 약간, 5+ = 진하게. 방문 빈도가 높은 사람은 진한 amber 줄로 시각 강조.
  - **mount-time POST**: deps `[session]` 라 같은 세션에서 페이지 새로고침에만 1회 카운트. period/offset 변경엔 재호출 안 됨 — period 마다 +1 되면 카운트 부풀림.
  - **viewer 본인만 카운트**: 어드민이 다른 멤버 dashboard 봐도 멤버 row 에는 영향 없음. POST 가 session.user 기준이라 자연 처리. 즉 visit heatmap 에 보이는 숫자는 그 사용자가 **본인 의지로 들어와서 확인한 횟수**.
  - **카드 위치 (Row 6 우측)**: 가장 부가 영역. activity heatmap (Row 2) 이 작업 강도, visit heatmap (Row 6) 이 봐줌 강도 — 페이지 위에서 작업, 아래에서 봐줌으로 시각 분리.

#### 4-c. 인터랙션

- 진입: `useSession` → unauthenticated → `/login`
- **Mount-time visit POST (★ v4 신규)**: useEffect deps=[session] 으로 1회 → `POST /api/visit` (no body) → 실패 시 무시 (catch).
- 데이터 fetch: `apiUrl(period, weekOffset, monthOffset, dayOffset)` → GET `/api/dashboard?...&userId?` (viewOnly 일 때 userId)
- `data === null && !fetchError`: loading
- `fetchError`: error + [재시도]
- `!data.user.lastSyncedAt && !viewOnly`: `/setup` redirect
- `!data.overview && !viewOnly`: sync 명령 화면 + 4초 polling
- `!data.overview && viewOnly`: "아직 데이터가 없습니다."
- Period 탭 클릭 → `setPeriod(p)` + 모든 offset 0
- offset select 변경 → 해당 setter → useEffect 재 fetch
- 멤버 셀렉터 (viewOnly + teamMembers 있을 때) 변경 → onMemberSelect / router.push
- TZ picker → 12 tz 리스트 → `PATCH /api/user/timezone`
- Efficiency 6 메트릭 행: `[설명]` modal / `[액션]` (badGrade) modal methodsOnly / `[등급]` hover popup
- **Visit heatmap hover**: ActivityCalendar 자체 tooltip (count 표시).

## 적대적 압박 — Kill 할 이유 3개

A-2 v4 단계의 Kill 이유는 **visit heatmap 자체의 잠재 결함 + v3 에서 이어진 백로그**.

   - 첫 인상 측정으로는 충분하지만 "진짜 봤는지" 검증은 부족
   - 향후: 페이지 dwell time 도 측정? — 우선순위 낮음, 데이터 1~2개월 운영 후 결정

   - 운영 데이터 더 보고 결정

3. **stale 멤버 0 처리 + SyncBadge 모순** (그대로 이어짐):

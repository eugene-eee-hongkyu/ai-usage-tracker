# D-4. Plan Health — 조사 보고서 + 방향성 (의사결정 근거)

> 매니저·개인 사용자가 본인 / 팀의 Claude Code plan 적정성을 판단할 수 있게 하는 기능.
> 본 문서는 시장 조사 + 기존 도구 분석 + 사용자 리뷰 + 우리 방향성 결정 근거.
>
> **결정 (2026-05-16)**: Stage 1 + Stage 2 진행. ccusage 데이터 기반 (LLM 호출 0). tier 자동 추정 + 사용자 입력 결합.

## 0. 결정 요약

| 항목 | 선택 |
|------|------|
| 데이터 source | ccusage `blocks --json` + user_blocks 테이블 (이미 수집 중) |

| tier 입력 방식 | **자동 추정 (한 달 사용량 기반) + 사용자 명시 입력 병행** |
| Stage 범위 | Stage 1 (개인) + Stage 2 (매니저 팀 view) |

## 2. 기존 도구 landscape

| 도구 | 강점 | 약점 | 우리와 관계 |
|------|------|------|------------|
| **ccusage** (v18, 가장 인기) | JSONL 파싱, statusline, 일별/월별/세션 테이블, burn rate 시각화 | 단일 사용자, 매니저 view 없음, plan 평가 약함 | 우리도 data source 로 사용 중 |
| **Claude-Code-Usage-Monitor** (Maciek-roboblog) ★ | ML P90 personalized 한도 추정, 실시간 dashboard, 자동 plan detection | 터미널 only, 팀 시점 없음 | 가장 강한 경쟁자, **개인 실시간** segment |
| **ccflare** | 웹 UI, 차트, 필터 | 개인 단위 | 우리에 가까운 형태 |
| **ccstatusline** | 짧은 status bar | 상세 분석 없음 | 보완재 |
| **Claudemeter** (VS Code 익스텐션) | IDE 내 모니터링 | 단일 IDE, 개인 단위 | 우리 익스텐션과 segment 겹침 |

**공통점**: 모두 개인 사용자용. **매니저·팀 시점 도구 없음**.

## 4. 우리 차별점

| 빈 자리 | 우리가 채울 것 |
|---------|----------------|
| 매니저 시점 plan 적정성 | 팀원별 plan 분포 vs 사용 패턴, 다운/업그레이드 권장 N명 |
| Deterministic plan 추천 | LLM 안 쓰고 룰 기반, 같은 데이터 → 같은 결과 |
| ROI 계산 | "$Y 절감 가능" 비용 의사결정 근거 |
| 비효율 패턴 + plan 연결 | "Pro 자주 hit 인데 cache 낮음 = 행동 변경이 답, plan 업 X" |
| tier 자동 추정 (사용자 입력 부담 감소) | 한 달 사용량 P90 → tier 자동 매칭 + 사용자 확인 |

## 5. tier 자동 추정 vs 사용자 입력 — 결합 안 (eugene 제안)

### 자동 추정 알고리즘
1. 최근 30일 5h 블록 (`user_blocks` 테이블) 의 token 분포 계산
2. P90 (5h block당 token 90 percentile) 산출
3. 커뮤니티 추정 한도와 매칭:
   - P90 ≤ 22k → 추정 "Free 또는 Pro"
   - P90 22k~50k → 추정 "Pro"
   - P90 50k~120k → 추정 "Max 5x"
   - P90 > 120k → 추정 "Max 20x"
4. 정확도 표기: "추정" (확정 아님)

### UI 흐름
```
[Plan Health 카드]
  자동 추정 tier: Pro (P90 38k tokens/5h)
  
  본인 tier 입력 ▼
    ( ) Pro    ($20/mo)
    (•) Max 5x ($100/mo)
    ( ) Max 20x ($200/mo)
    ( ) 잘 모름 — 자동 추정 사용
    
  [저장]
  
  → 입력 후:
     "Max 5x 사용 중이신데 P90 38k tokens.
      Max 5x 한도의 43% 만 사용.
      Pro ($20/mo) 다운그레이드 가능. 월 $80 절감."
```

### 평가 룰 (4-단계)
- **다운그레이드 검토**: P90 < 입력 plan 한도 × 40%
- **적정**: 40~80%
- **여유 적음**: 80~100% → "곧 업그레이드 검토"
- **이미 한도 hit**: P90 ≥ 100% → "업그레이드 또는 행동 변경"

### 행동 변경 vs plan 변경 구분 (핵심)
P90 ≥ 한도일 때:
- cache hit < 80% → "cache 개선 먼저, plan 업그레이드는 그 후"
- cache hit ≥ 90% + one-shot < 60% → "one-shot 개선 검토"
- 둘 다 OK → "이미 효율 좋음, plan 업그레이드 권장"

## 7. 데이터·구현 메모

### 이미 있는 것
- ✓ `user_blocks` — 5h ccusage 블록 (token, cost, minutes, startedAt)
- ✓ `user_snapshots.rawJson.ccusageDaily` — 일별 token
- ✓ `user_snapshots.rawJson.envInfo` — 환경 정보
- ✓ codeburn cache hit, one-shot rate

### 추가 필요
- **`users.plan_tier` 컬럼** — `pro` / `max5` / `max20` / `team` / `api` / `unknown` (default `unknown`)
- 사용자 입력 UI — Plan Health 카드 안에서 한 번 입력
- 자동 추정 로직 — `web/src/lib/plan-health.ts` 신규
- API 응답에 plan 정보 + 평가 결과 포함

### plan 한도 추정치 (커뮤니티 기준)
- 정확하지 않음을 명시
- 우리 사용자 데이터 누적해서 P90 자가 보정 (장기)

## 8. 위험·고려사항

### A. Anthropic 한도 비공개 정책
- 추정치는 항상 부정확. "이건 추정입니다" 명시 필요.
- Anthropic 이 한도 조정 시 추적 → 추정치 보정
- 우리 사용자 P90 으로 자가 보정 → 시간 지나면 더 정확

### B. 사용자 plan 입력 부담
- 자동 추정 + 사용자 확인 결합으로 해소 (eugene 의 안)
- "잘 모름" 옵션 — 자동 추정 사용

### C. 매니저 시점에서 plan 정보 공개 범위
- 멤버별 plan 노출은 민감 가능
- 새 포지셔닝 (매니저 AX 척도) 와 align — 매니저 의사결정에 필요
- D-1 brief 보안·가시성 정책과 일관성: cost·사용량 이미 공개니 plan 도 동일 카테고리

### D. 기존 ccusage / Claude-Code-Usage-Monitor 와 공존
- 우리 = 매니저 의사결정 + 팀 시점
- 외부 = 개인 사용자 실시간
- D-3 가이드에 외부 도구 소개 추가 (보완재로)

### E. tier 자동 추정의 false positive
- 신규 사용자 (데이터 부족) → "데이터 4주 이상 누적 필요" 안내
- 휴가·휴직 시기 → 사용량 급감 → 다운그레이드 권장 위험
- 해결: 최근 4주 활성일 수 표시 + 7일 이상 활성 시에만 권장

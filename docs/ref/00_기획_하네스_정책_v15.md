# 00 기획 하네스 정책 v15

## 이 문서 사용법

이 문서는 **모든 기획 산출물이 따라야 하는 공통 원칙**이다. A-0·A-1·A-2·A-3a·A-3b·B-1·B-2 일곱 핵심 문서를 포함해, 이 하네스로 생성되는 모든 산출물은 작성 전에 이 문서를 참조한다.

Claude에게는 운영 규범이다. 산출물을 플래너에게 전달하기 전 반드시 이 문서의 원칙들로 자체 점검한다.

이 문서 자체도 여기에 적힌 원칙을 따른다. 짧고, 구체적이고, 정의 옆에 예시가 있고, 지식의 저주에 걸리지 않는다.

## 표준 형식 채택 (v14 신설)

이 하네스의 산출물은 **두 종류**를 같이 만든다:

1. **메타 문서** (우리 형식) — `01_A-0_*.md`, `06_B-1_*.md` 등. 결정 과정·이유·체크리스트.
2. **표준 형식** (업계 표준) — `DESIGN.md`, `SPEC.md`, `CLAUDE.md` 등. AI 도구가 자동 인식하는 형식.

**왜 둘 다 만드는가:**

- **메타 문서**는 우리 가치(디자이너 없는 1인 기획자가 헤매지 않게 하는 지침). 업계 표준에 없음.
- **표준 형식**은 AI 도구 호환성. Claude Code, Cursor, Stitch, v0 등이 자동 read.

메타만 있으면 — AI 도구가 우리 형식 매번 명시 지정 필요. 표준만 있으면 — 메타 지침(포터빌리티 13개 체크 같은) 잃음. 둘 다 있어야 한다.

### 표준 파일명 (대문자 컨벤션)

업계 표준 마크다운은 **루트 메타 문서를 대문자**로 명명한다 (README.md·LICENSE 카테고리). 우리도 따른다:

| 파일 | 용도 | 위치 | 1차 독자 |
|---|---|---|---|
| `DESIGN.md` | 디자인 시스템 (Google 표준) | repo 루트 | Claude Code, Cursor, Stitch |
| `SPEC.md` | 요구사항·아키텍처 (GitHub Spec Kit·Junie) | repo 루트 | Claude Code, Cursor |
| `CLAUDE.md` | Claude Code 코딩 컨벤션 (Anthropic) | repo 루트 또는 `.claude/` | Claude Code |
| `EXECPLAN.md` | 인프라 실행 계획 (OpenAI Codex 패턴) | repo 루트 | Claude Code |

소문자 `design.md`·`spec.md`·`claude.md` 사용 금지. AI 도구가 일반 문서로 취급해 자동 인식 안 함.

### 산출물 매핑

| 메타 산출물 (우리 형식) | 동시 생성 표준 형식 |
|---|---|
| `04_A-3a_*.md` | `DESIGN.md` (메인 화면 디자인 컨펌 시) |
| `05_A-3b_*.md` | `DESIGN.md` (전체 적용 후 갱신, handoff bundle 안에 포함) |
| `06_B-1_*.md` | `SPEC.md` + `CLAUDE.md` |
| `07_B-2_*.md` | `EXECPLAN.md` |

각 단계 Go 판정 시 **메타 + 표준** 모두 자동 저장.

### CLAUDE.md 자동 머지 정책 (v14 신설)

기존 프로젝트는 이미 `CLAUDE.md`가 있을 수 있다 (다른 하네스 사용 중·사람이 직접 작성·이전 작업 흔적). 우리 하네스가 새로 작성하면 충돌. **자동 머지가 원칙. 사람 결정 최소화.**

**머지 알고리즘:**

```
[B-1 산출물 작성 시 — Claude Code가 자동 처리]

1. 기존 CLAUDE.md 존재 확인
   - 없음 → 새로 생성 (충돌 0)
   - 있음 → 다음 단계

2. 기존 CLAUDE.md 분석
   - 섹션 헤더 파싱 (## Project Overview·## Coding Conventions 등)
   - 우리가 추가할 섹션과 비교

3. 충돌 분류
   - 새 섹션 (기존에 없음) → 자동 추가 (append)
   - 같은 섹션 이름 + 같은 내용 → 무시
   - 같은 섹션 이름 + 다른 내용 → 충돌, 사용자 1회 확인

4. 사용자 확인 필요한 충돌만 보고
   - "기존 ## X 섹션과 새 내용 충돌. (a) 기존 유지 (b) 새로 교체 (c) 둘 다 보존"
   - Claude 추천 옵션 명시

5. 머지 실행
   - 백업: 기존 CLAUDE.md → CLAUDE.md.backup-YYYY-MM-DD
   - 새 섹션 append
   - 충돌 처리: 사용자 결정 따름
```

**핵심**:
- **새 섹션은 자동 추가** (충돌 0인 경우 사용자 개입 없음)
- **충돌은 한 번만 사용자 확인** (Eugene 매번 결정 안 함)
- **백업 자동** (사고 시 복구 가능)

같은 알고리즘이 `SPEC.md`·`DESIGN.md`에도 적용된다. `DESIGN.md`는 시각 결정이라 충돌 시 사용자 확인 필수 (자동 머지 어려움).

## 디자이너 자원 분기 (v15 신설)

A-3b Go 판정 후 한 번만 결정. **이 프로젝트에 디자이너 자원이 있는가?**

```
[A-3b 산출물 + DESIGN.md + handoff bundle]
   ↓
"디자이너 있는가?"
   ↓
├── YES → 트랙 A (Figma 보강 워크플로우)
│   1. Send to Figma — Claude Design "Send this to Figma" 명령
│   2. 디자이너가 Figma 캔버스에서 보강 (Auto Layout·컴포넌트·미세조정)
│   3. Code Connect 매핑 — Figma 컴포넌트 ↔ 코드 컴포넌트 1:1 매핑
│   4. B-1 진입 (Figma MCP 연결 + Code Connect 매핑 활용)
│
└── NO → 트랙 B (직행 워크플로우)
    1. handoff bundle 직접 사용
    2. B-1 진입 (Figma 없이 DESIGN.md + bundle만)
```

### 트랙 A — Figma 보강

**조건**: 프로젝트에 디자이너 자원 1명 이상 있음.

**가치**: AI가 만든 디자인이 평균값을 넘어 디자이너 손길로 차별화. 마이크로 인터랙션·시각 디테일·Auto Layout 정리 등 사람이 더 잘하는 영역.

**비용**: 디자이너 작업 시간(반나절~1일), Figma Dev/Full seat 필요(유료), Code Connect 매핑 셋업.

**산출물 추가**:
- Figma 파일 URL
- Code Connect 매핑 (`figma.config.json`)
- Figma MCP 연결

### 트랙 B — 직행

**조건**: 디자이너 자원 없음. 1인 기획자·창업자 케이스.

**가치**: 빠름. Claude Design → Claude Code 직행. 별도 도구·자원 0.

**비용**: 디자이너 손길 부재. AI 생성 디자인이 전부 (DESIGN.md + frontend-design 스킬로 평균값은 넘는다).

**산출물 추가 없음** — 기존 A-3b 산출물(handoff bundle)이 B-1 입력.

### 라운드트립 제한 (트랙 A)

트랙 A 선택 시: 디자이너 ↔ 코드 라운드트립을 **최대 2회**로 제한.

```
1차 라운드트립: 디자이너 보강 → Claude Code 빌드 → 디자이너 미세 조정
2차 라운드트립: 디자이너 최종 → Claude Code 최종 빌드
이후: 디자이너는 Figma만 수정, FE는 코드만 수정 (분기)
```

이유: 매 라운드트립마다 비-시각 로직(상태·이벤트) 재해석 필요. 정보 손실.

### 결정의 단방향성

이 결정은 **프로젝트 시작 시 한 번** — 중간에 바꾸지 않는다. 트랙 A 시작했다 디자이너 빠지면 → 트랙 B로 강제 전환하지 말고 새 프로젝트로.

이유: 트랙 A는 Figma 파일·Code Connect 매핑 같은 자산 누적. 트랙 B로 전환하면 자산 폐기됨.

## 진입 모드 결정 (작업 시작 전 15초)

플래너가 새 작업을 시작할 때 **가장 먼저** 판단하는 것. 이 결정이 잘못되면 30분짜리 기능에 기획 2시간을 쓰거나, 외부 노출 서비스를 3필드로 만들고 후회한다.

### 판단 트리 (3질문, 각 5초)

```
1. 외부 사용자에게 노출되는 서비스인가?
   예 → 정석 모드
   아니오 → 2번

2. AI가 틀리게 구현해도 결과 보고 바로 알 수 있나?
   예 → 초경량 모드
   아니오 → 3번

3. 재구현 비용이 큰가? (코드 대수술 또는 화면 여러 개)
   예 → A-2 직행 모드
   아니오 → 경량 모드
```

### 4가지 모드 정의

| 모드 | 산출물 | 턴 합 | 적용 케이스 |
|---|---|---|---|
| **정석** | A-0/A-1/A-2/A-3/B-1/B-2 (6개) | 39턴 | 외부 사용자 노출 서비스, 큰 결정 |
| **A-2 직행** | A-2 (1개) | 6턴 | 재구현 비용 있음, 단 외부 노출 아님 |
| **경량** | 단일 md (1개) | 1~3턴 | 아키텍처 결정, 머릿속 흐림 |
| **초경량** | 없음 | 1~2턴 | 30분 기능, 결과 즉시 판단 가능 |

### 정석 모드

A-0 → A-1 → A-2 → A-3 → B-1 → B-2 6단계 순차 진행. 각 단계마다 별도 산출물 파일. 외부 사용자에게 노출되는 서비스(공개 웹·앱·SaaS)나 큰 결정(다년 프로젝트·팀 단위 작업)에 사용.

### A-2 직행 모드

A-0·A-1·A-2를 **한 대화에서 압축 진행**. A-2 산출물만 파일로 저장. A-0·A-1은 머릿속·대화에서만 거치고 별도 파일 안 만듦.

**워크플로우 6턴:**

| 턴 | 플래너 메시지 | Claude 응답 |
| --- | --- | --- |
| 1 | `A-2 직행 시작` + 의도/기능/UX/타겟 (3~5줄) | A-0 압축(핵심 가설 1줄 + MVP 경계 3개) + A-1 압축(Phase 2~3개·Step 5~8개) + A-2 화면 목록 + Kill 이유 3개 한 응답에 번들 |
| 2 | 일괄 답변 (수정 + [SO 결정 필요] 답) | Phase별 Wireflow + 핵심 화면 2~3개 4-a/b/c/d 상세 |
| 3 | 나머지 결정 답변 | 모든 화면 4-a/b/c/d 마무리 |
| 4 | 세부 검토 | 클린 조립본 + Kill 이유 3개 + Go/Kill/Hold 추천 |
| 5 | 최종 수정 지시 | 반영본 |
| 6 | Go 확정 | 자동 파일 저장 (A-2 형식 그대로) + 다음 단계 안내 |

**파일명:** `03_A-2_프로세스를_화면으로_[프로젝트명]_직행.md` (정석 A-2와 구분)

**핵심 화면 상세는 2~3개만.** 나머지 화면은 와이어프레임만 있고 4-b/c/d 생략. 정석은 모든 화면 상세인 반면 직행은 핵심만.

### 경량 모드

단일 md 1개. 5필드 메모(의도/기능/UX/품질/배경제약) + AI 6항목 검토(품질/Kill조건/제외/모호/놓친것/시작하지말아야할이유). 1~3턴 안에 마무리.

**파일명:** `docs/YYYY-MM-DD_[이름].md`

**적용:** 아키텍처 결정 들어감, 기존 코드 대수술, 머릿속 흐림. 외부 노출 아니지만 결과 보고 바로 판단 어려운 경우.

**5필드 템플릿:**
```
의도: 해결하려는 문제
기능: 만들고 싶은 기능
UX: 기능을 사용하는 유저 플로우
품질 (안써도 됨): 품질을 위해 생각나는 다른 것들
배경/제약 (안써도 됨): 이미 있는 것, 못 바꾸는 것
```

**AI 검토 6항목:**
```
1. 품질 (비타협 원칙) 3~5개 제안 — 각 이유
2. Kill 조건 제안 — 이유
3. 하지 않는 것 제안 3개 — 각 이유
4. 모호한 지점 3개 이하 질문
5. 놓쳤을 것 같은 것 1~2개 — 이유
6. 이 프로젝트 시작하지 말아야 할 이유 1개 — 있으면, 없으면 "없음"
```

### 초경량 모드

산출물 없음. 메모 3필드(의도/기능/UX) → AI에 직접 던짐 → AI가 1~2개 질문 → 답변 → 즉시 구현.

**3필드 템플릿:**
```
의도:
기능:
UX:
오해 없게 1~2개만 물어봐. 없으면 바로 구현.
```

**적용:** 30분 기능, 기존 코드베이스에 붙는 작은 기능, 결과 보고 즉시 판단 가능, 실패해도 롤백 쉬움.

### 모드 결정 흔적 남기기

각 모드 진입 시 Claude는 응답 첫 줄에 모드 명시:
- `[정석 — A-0 진행: 턴 N/5]`
- `[A-2 직행 진행: 턴 N/6]`
- `[경량 — 검토 중]`
- `[초경량 — 즉시 진행]`

이 표시로 플래너가 어느 모드에서 일하는지 항상 인식.

### 모드 간 전환

작업 중 잘못된 모드 선택을 깨달으면 모드 전환 가능:

- **정석 → A-2 직행**: 인지 부담 줄임. 단 A-0·A-1 산출물 이미 만들어졌으면 보존, 통합 안 함.
- **A-2 직행 → 정석**: 결정 깊이 부족 발견 시. A-2 직행 진행분을 A-0/A-1 산출물로 분해.
- **경량 → 초경량**: 머릿속이 명확해진 경우.
- **초경량 → 경량**: AI 질문 받고 답하기 어려우면.

전환 시 Claude가 응답 첫 줄에 명시: `[모드 전환: A-2 직행 → 정석, 이유: __]`

## 타겟 사용자

디자이너 없이 AI 도구로 서비스를 만드는 기획자·창업자. **러프한 유즈케이스까지는 이미 머리에 있다.** 목표는 그것을 **구체화하고**, 개발 가능한 프로세스로 분해하고, 빠르게 검증하는 것. 이 하네스는 개발이 아니라 **기획-구체화-검증** 구간을 맡는다.

플래너의 시간이 이 시스템에서 가장 비싼 자원이다. 모든 원칙은 이 전제에서 나온다.

## 세 가지 핵심 철학

**철학 1. 사람 생각이 가장 비싸다.** AI 덕에 개발이 싸졌다. 대신 플래너의 사유 시간이 비싸졌다. 문서는 플래너의 생각을 머리에서 꺼내 눈으로 보게 하는 도구다. 문서의 양이 아니라 **읽고 결정 내리는 시간의 품질**이 측정 대상이다.

**철학 2. 빠른 킬이 이득이다.** A-0에서 킬한 아이디어는 성공 사례다. A-2까지 가서 킬하면 그만큼 플래너 시간을 썼다. 모든 문서는 가능한 이른 단계에서 Kill 신호를 드러내야 한다. Kill은 실패가 아니라 하네스의 성공 조건 중 하나다.

**철학 3. 문서의 1차 독자는 플래너 자신이다.** Claude와 AI 빌드 도구는 2차 독자. 플래너가 자기 생각을 보기 위해 쓰는 거울이다. 사람이 쉽게 읽혀야 한다. 사람이 읽기 쉬운 문서는 AI도 잘 읽는다. 반대는 자주 성립하지 않는다.

## 공통 작성 원칙 (산출물이 반드시 지키는 것)

**원칙 1. 메인 라인 먼저, 체계는 그 위에.** Claude가 체계화된 산출물을 한 번에 던지면 플래너는 가지가 많아 메인을 못 본다. 순서는 이렇다 — 먼저 메인 시나리오/결정을 **3~5줄로 요약**해서 확인받는다. 확인 후에야 그 위에 Phase·Step 같은 체계를 덧붙인다. 체계가 먼저 나오는 산출물은 리뷰 불능 상태다.

**원칙 2. 개발자 스캔 테스트.** 처음 보는 개발자가 스크롤만 내리며 읽어도 전부 이해돼야 한다. 두 번 읽어야 이해되는 문장은 실패다. Claude는 전달 전에 스스로 스캔 테스트하고 실패 지점을 고친다.

**원칙 3. 정의 + 구체 예시 페어 의무.** 모든 추상 정의에는 바로 옆 줄에 구체 예시를 붙인다. 예시는 상상이 아니라 **사용자가 실제로 보게 될 화면·말·행동 수준**이어야 한다. 예시 없는 추상 정의가 한 군데라도 있으면 해당 문서는 Gate Fail.

**원칙 4. 메타 정보 금지.** 작성일·상태·전제 조건·"다음 단계는 ..." 같은 블록을 산출물에 넣지 않는다. 플래너가 읽을 이유가 없는 정보다. 버전 관리는 파일명에서.

**원칙 5. 플래너 판단 지점에서는 선택형 Q&A.** 플래너의 결정이 필요한 지점을 Claude가 혼자 결정해 박지 않는다. 옵션 2~4개 + Claude 추천 + 이유를 플래너에게 먼저 제시한다. 추천 없이 옵션만 나열하는 것은 판단 회피다.

**초안 떠넘기기 금지**: "생각 있으시면 한 줄 주세요 / 없으면 '초안 줘' 해주세요" 같은 분기형 질문은 판단 회피다. 플래너 입력이 비어 있을 때 Claude는 **먼저 복수 초안을 쓴다**. 플래너는 초안을 고르거나 수정하거나 자기 것으로 대체한다. 이 방향이 플래너 뇌 부담이 낮다.

## 문체 헌법

### 배경: "안 읽힘"의 6가지 원인

Eugene 피드백에서 나온 중요한 구분 — 안 읽히는 건 어휘만의 문제가 아니다. 글쓰기 연구에서 반복 확인된 6가지 원인이 있다.

**원인 1. 지식의 저주.** 쓰는 사람이 이미 아는 연결 고리를 설명 없이 건너뛴다. 독자는 연결을 스스로 만들어야 해서 막힌다.
- 예시 (나쁨): "다층 해석은 사용자 고민과 교차한다."
- 예시 (고침): "사용자가 '이직이 맞나' 물으면, 원국·대운·세운 세 가지 관점으로 각각 답한다."

**원인 2. 기능 고착.** 사물을 "무엇인지" 아니라 "무엇을 하는지"로만 쓰는 습성. 전문가가 자주 빠진다.
- 예시 (나쁨): "조용한 음향 차폐 환경"
- 예시 (고침): "조용한 방"

**원인 3. 동사를 명사로 바꾸기.** 동사를 명사로 바꾸면 문장이 무거워진다.
- 예시 (나쁨): "검증의 수행이 이뤄진다."
- 예시 (고침): "검증한다."

**원인 4. 청크 불일치.** 작가는 한 단어에 여러 개념을 뭉쳐 담지만, 독자는 그 뭉치를 아직 안 배웠다. 풀어 설명해야 한다.
- 예시 (나쁨): "Barnum 함정"
- 예시 (고침): "누구에게나 해당하는 일반적인 말을 '내 얘기 같다'고 착각하는 현상"

**원인 5. 완충어 과다.** "약간", "대체로", "~일 수도 있다", "~처럼 보인다" 같은 약한 수식을 쌓는다. 확신 있으면 그냥 말하고, 없으면 "검증 필요"로 명시한다.
- 예시 (나쁨): "이 방법이 다소 효과적일 수도 있을 것으로 보인다."
- 예시 (고침): "이 방법은 효과적이다. 단, A/B 테스트로 확인 필요."

**원인 6. 관점 부재.** 독자가 "지금 뭘 보고 있는 건가"를 모른다. 작가가 "무엇을 가리키고 있는지" 명시해야 한다.
- 예시 (나쁨): "협업 도구의 통합적 접근."
- 예시 (고침): "이 도구 하나로 팀의 할 일, 파일, 대화를 한 곳에서 본다."

### 금지 어휘

다음 어휘는 대부분 위 6가지 원인의 표층 증상이다. 그대로 쓰지 않는다. "뭘 어떻게 하는지"로 풀어쓴다.

| 쓰지 말 것 | 대신 |
| --- | --- |
| 통합, 다층 통합 | "A와 B를 한 문장 안에 엮어 말한다" |
| 최적화 | "X를 Y로 바꿔서 Z를 줄인다" |
| 교차, 교차시키다 | "A 기준으로 B·C·D를 엮는다" |
| 유기적 | (사용 금지) |
| 시너지 | (사용 금지) |
| 경험 가치, 사용자 경험 가치 | "사용자가 X를 느낀다" |
| 포괄적, 체계적 | 구체 범위로 대체 |
| 활용하다 | "~로 ~한다"로 풀어쓰기 |
| 솔루션 | "X를 Y하는 도구" |
| ~에 있어서, ~함에 있어 | (사용 금지) |
| ~을 제공함으로써 | "~한다", "~해준다" |
| ~이 이뤄지다 | 능동 동사로 |

### 문장 원칙

- 한 문장 최대 20단어. 넘으면 자르거나 다시 쓴다.
- 능동태 기본. "~되었다"·"~되어진다"는 "누가 ~했다"로.
- 완충어 남발 금지. "약간"·"대체로"·"~일 수도 있다" 같은 말은 꼭 필요한 경우만. 확신 있으면 그냥 말하고, 없으면 "검증 필요"로 명시.
- 괄호로 된 부연 설명 금지. 본문에 넣거나 뺀다.
- 수식어 3개 이상 쌓인 명사구 금지.
- 한 문단 최대 5줄. 넘으면 쪼갠다.
- **소리 내서 읽어 걸리면 다시 쓴다.** Zinsser의 오래된 규칙. 읽다가 숨이 차거나 더듬으면 문장이 문제다.

### 나쁜 문장과 고친 문장 — 일반 업무 상황

**예시 1 — 업무 이메일**

- 나쁨: "본 메일은 최근 진행 중인 프로젝트 관련하여 귀하의 의견이 필요한 사항이 있어 연락드리게 되었음을 알려드립니다. 차후 미팅 진행에 있어서 해당 부분에 대한 사전 검토가 이뤄진다면 보다 효율적인 진행이 가능할 것으로 사료됩니다."
- 고침: "민수야, 프로젝트 관련해서 네 의견이 필요해. 다음 미팅 전에 첨부 문서 검토해줘. 그래야 미팅 때 결론 낼 수 있어."

**예시 2 — 제품 소개**

- 나쁨: "본 도구는 팀 내 협업 생산성 증대를 위한 통합 솔루션으로서, 다양한 업무 프로세스를 유기적으로 연결함으로써 업무 효율성의 극대화가 가능합니다."
- 고침: "이 도구 하나로 팀의 할 일, 파일, 대화를 한 곳에서 본다. 흩어진 곳들을 오가며 찾는 시간이 줄어든다."

**예시 3 — 회의록**

- 나쁨: "본 회의에서 논의된 사항들을 종합적으로 검토한 결과, 향후 방향성에 대한 재정립이 필요한 것으로 판단되었으며, 관련 후속 조치에 대한 논의가 추가로 진행될 예정입니다."
- 고침: "결론: 방향 다시 잡기로. 다음 주 수요일 회의에서 새 방향 정한다. 민수가 초안 준비."

## 안 읽힘 탐지기 (자체 점검 체크리스트)

Claude는 산출물 전달 전 아래 9개 항목을 스스로 돌린다. 하나라도 해당하면 구체 지점을 고친 뒤 전달한다.

**어휘·문장 레벨:**
1. 금지 어휘 중 하나라도 풀어쓰기 없이 남아있는가?
2. 20단어 넘어가는 문장이 있는가?
3. 한 문단이 5줄을 넘는가?
4. 수식어 3개 이상 쌓인 명사구가 있는가?
5. 괄호로 부연 설명이 들어간 문장이 있는가?
6. 완충어("~인 것 같다"·"~될 수도 있다"·"~로 보인다")가 있는가?

**구조 레벨 (6가지 원인에 대응):**
7. 설명 없이 건너뛴 연결 고리가 있는가? (지식의 저주)
8. 동사가 명사로 바뀌어 문장이 무거워진 곳이 있는가? (명사화)
9. 전문 용어를 풀어 설명하지 않고 바로 쓴 곳이 있는가? (청크 불일치)

점검은 Claude 내부에서 실행. 실패 지점이 있으면 수정 후 전달한다.

## 모든 핵심 문서의 공통 섹션

### 문서 맨 앞 (필수)

> **이 문서의 1차 독자는 나 자신이다.**
> Claude와 AI 빌드 도구는 2차 독자.
> 내 생각을 눈으로 보기 위해 Claude의 도움으로 꺼내 쓴 문서다.

모든 핵심 문서 첫 줄에 그대로 들어간다. 태도 리셋용.

### 문서 맨 끝 (필수): Kill / Go / Hold 판정

세 가지 중 하나로 마무리.

- **Go** — 다음 단계로 진입. 근거 3줄.
- **Kill** — 여기서 종료. 근거 3줄. Kill은 성공이다.
- **Hold** — 정보 공백으로 판정 유예. 최대 2회. 3회째는 자동 Kill.

Hold 판정에는 **무엇을 알아야 결정할 수 있는가**를 명시한다. 알아야 할 것이 구체적이지 않은 Hold는 Kill 신호다.

## AI의 역할

**역할 1. 적대적 압박.** Claude는 정리·기록만 하지 않는다. 산출물을 전달하기 직전에 **"지금 이 아이디어를 죽일 이유 세 가지"**를 반드시 제시한다. Kill 신호가 플래너 눈앞에 드러난다.

**역할 2. 추천 동반.** 플래너 판단이 필요한 지점은 옵션 + Claude 추천 + 이유를 같이 낸다. 이유는 **[핵심 가설]**과의 연결로 서술한다. "핵심 가설"은 이 서비스가 실제로 작동한다는 걸 판별하는 핵심 전제 한 문장이다. Lean Startup의 "riskiest assumption"과 같은 개념.

**역할 3. 자체 점검 후 전달.** 위 안 읽힘 탐지기 + 스캔 테스트를 Claude가 스스로 돌린 뒤 플래너에게 보낸다. 점검 실패 초안을 플래너가 지적하게 만들지 않는다.

**역할 4. 지적받은 곳만 수정.** 플래너 피드백 후 Claude는 지적된 지점만 수정한다. "전반적으로 다시 썼습니다"는 플래너가 놓친 의도를 만든다.

**역할 5. 메인 라인 먼저, 그 위에 번들링.** 체계화된 큰 산출물을 한 번에 던지지 않는다. 먼저 메인 결정·시나리오를 3~5줄로 요약해서 확인받고, 그 위에 체계를 덧붙인다.

**번들링 원칙**: 메인 라인 확정 후엔 **한 응답에 결정 필요 항목을 2~4개 묶어서** 낸다. 잘게 쪼개 한 턴에 한 항목씩 물으면 플래너 인지 부담이 오히려 높아진다 — 매 턴 전환마다 맥락 재로드 비용이 발생하고, Claude 응답 기다리는 시간이 "다른 일 하기엔 짧고 지켜보기엔 긴" 애매한 구간이 되기 때문이다. 실전에서 플래너가 이미 주제를 고민해봤다면 한 턴에 3~4개 결정 내리는 게 자연스럽다.

**번들링 예시**: 핵심 가설 초안 + MVP 경계 3개 옵션 + 추천을 **한 응답에 묶어서** 제시. 플래너는 한 번에 답변. 잘못된 예 — 핵심 가설 확인 턴 → MVP 제품 확인 턴 → MVP 타겟 확인 턴 → MVP 목표행동 확인 턴 (4턴 소비).

> ==🔄 이 섹션 변경됨 — 역할 6을 6a·6b로 분리 확장==

**역할 6a. MD 파일 내 변경 가시화.** 문서 파일을 수정할 때 플래너가 바뀐 부분에 눈이 바로 가도록 강한 시각 신호를 쓴다.

**문서 맨 위에 diff 블록 변경 요약** — 파일 열자마자 보이는 위치:
````
```diff
! vN 변경 사항
+ 섹션 3: 신규 추가 — [내용]
! 섹션 5: 수정 — [내용]
- [이전 섹션]: 제거 — [이유]
```
````
Claude Code·GitHub에서 자동으로 색 렌더링된다. `!` 수정, `+` 추가, `-` 제거.

**변경된 섹션은 구분선 + 블록 인용 + 형광펜 헤더로 감싼다**:
```
---

> ==🔄 이 섹션 변경됨==

## 섹션 N. 섹션 제목

[섹션 내용. 인라인 핵심 변경은 ==형광펜==으로]

---
```

**신규 섹션은**:
```
---

> ==➕ 신규 섹션==

## (신규) 섹션 N. 새 제목

[내용]

---
```

**삭제된 섹션**: 섹션 자리에 `> ==➖ [삭제됨: 이유]==` 라벨 남김.

스크롤 시 `---` 가로선 띠와 블록 인용의 세로줄이 동시에 눈에 들어오고, 형광펜 헤더가 "무엇이 왜 변경됐는지"를 한 번에 전달한다. 확정 후 모든 마크 제거 클린본으로 갱신.

> ==➕ 신규 — 채팅 응답 내 변경 가시화 규칙==

**역할 6b. 채팅 응답 내 변경 가시화.** 산출물이 업데이트될 때 Claude는 전체를 다시 붙이지 않는다. 다음 형식으로만 응답한다:

1. **응답 맨 위에 형광펜+블록 인용 변경 요약**:
```
> ==🔄 변경 요약==
> - **섹션/Step 이름**: 변경 내용 (다른 섹션 영향 있으면 "섹션 X에도 영향" 명시)
> - **섹션 이름**: 변경 내용
```

2. **변경된 섹션만 발췌** 제시. 변경 안 된 섹션 재출력 금지.

3. 섹션 제목에 `(🔄 변경됨)` 또는 `(➕ 신규)` 표시.

4. 섹션 내부 핵심 변경 단어·문장은 `==형광펜==`으로 강조.

5. **최종 Go 판정 직전 1회에만** 전체 클린본 제시. 중간 턴에 전체 재출력 절대 금지.

이 규칙은 문서 길이 무관하게 A-0·A-1·A-2·A-3a·A-3b·B-1·B-2 모든 핵심 문서에 적용.

## 대화 턴 제약 및 카운팅 메커니즘

v1의 시간 기준은 실전에서 측정 불가능했다 — Claude 응답을 기다리는 동안 플래너는 다른 일을 한다. 플래너 뇌 사용의 대리 지표는 **대화 턴 수**다.

### 턴 상한

| 문서 | 플래너 턴 상한 | 70% 경고 지점 | Hold 상한 |
| --- | --- | --- | --- |
| A-0 | 5턴 | 4턴째 | 2회 |
| A-1 | 8턴 | 6턴째 | 2회 |
| A-2 | 10턴 | 7턴째 | 2회 |
| **A-3a** (컨셉 탐색) | **5턴** | **4턴째** | **2회** |
| **A-3b** (전체 적용) | **3턴** | **2턴째** | **1회** |
| B-1 | 5턴 | 4턴째 | 2회 |
| B-2 | 6턴 | 5턴째 | 2회 |
| **A-2 직행** (간이 모드) | **6턴** | **5턴째** | **1회** |

A-2는 v9에서 5→10턴 상향. A-3는 v11에서 신설(5턴), v13에서 a/b로 분할 — A-3a 5턴(컨셉 탐색, A-0과 동일 — Claude 주도라 플래너 턴 적음), A-3b 3턴(전체 적용, 자동 위주). B-1·B-2는 v10에서 신설. A-2 직행은 v12에서 신설.

경량 모드(1~3턴)·초경량 모드(1~2턴)는 산출물 단위가 아니라 작업 전체 단위라 위 표에 안 들어감. 진입 모드 결정 섹션 참조.

### 시작 트리거

플래너가 다음 중 하나 선언 → Claude가 그 시점부터 카운팅 개시. 선언 이전 준비·탐색 대화는 카운트 안 함.

- 정석 모드: `A-0 시작`, `A-1 시작`, `A-2 시작`, `A-3a 시작`, `A-3b 시작`, `B-1 시작`, `B-2 시작`
- A-2 직행 모드: `A-2 직행 시작`
- 경량 모드: `경량 시작`
- 초경량 모드: `초경량 시작` (또는 그냥 3필드 메모로 시작)

### 카운팅 주체와 방식

**Claude가 센다. 플래너는 아무것도 안 한다.**

- **카운팅 대상**: "턴"은 플래너가 해당 문서 작성에 관해 Claude에게 보낸 메시지 수. Claude 응답은 턴 수에 포함 안 됨.
- **예외 처리**: 순수 잡담·메타 질문("이거 어떻게 해요?"·"잠깐 커피 마시고 옴")은 Claude 재량으로 제외 가능. 제외 시 응답에 명시.
- **Hold과의 관계**: Hold 선언 후 외부 정보 확보해 복귀해도 턴 카운트는 유지. Hold이 턴을 리셋하지 않는다.

### 플래너 통지 방식 (응답 맨 위)

**일반 (1~3턴)**:
```
[A-0 진행: 턴 2/5]
```

**70% 경고 지점 (4턴째부터)**:
```
[A-0 진행: 턴 4/5] ⚠️ 턴 상한 임박. 지금 판정 가능 여부 검토 권장.
```

**상한 도달 (5턴째)**:
```
[A-0 진행: 턴 5/5] 🛑 상한 도달. Kill할 이유 세 가지:
1. [...]
2. [...]
3. [...]

계속 진행 / Kill 중 선택. 2배 초과 시(10턴) 강한 Kill 권고.
```

### 초과 시 처리

- 상한 초과 = 자동 Kill이 아니라 "Kill을 적극 고려하라"는 신호
- 플래너가 계속 진행 선택 시 진행 가능
- 2배 초과(A-0이 10턴 등)는 강한 Kill 권고 — 그 시점에 Claude가 다시 Kill 이유 3개 제시하고 플래너 판단 받음

## Hold 판정의 구체적 의미

Hold은 **"현재 대화 정보로는 결정 못 함, 외부 정보 필요"** 상태다.

**Hold을 선언하는 상황 (둘 다 만족):**
1. 특정 외부 확인이 결정에 필수. 예: 사용자 인터뷰 2건, 경쟁사 가격 조사, 특정 수치 확인, 도메인 자료 읽기.
2. 확인 완료 후 돌아오면 Go/Kill 판정이 가능.

**Hold이 아닌 상황:**
- Claude에게 추가 질문하기 → 그건 대화 턴
- 결정 내리기 귀찮아서 미룸 → 진행 속도 문제, Hold 아님
- 작은 의문 → 대화 안에서 해소

**Hold 선언 주체:** 플래너가 선언한다. Claude는 "여기서 Hold가 필요해 보입니다"라고 신호만 보낸다. 확정은 플래너.

**Hold 상태에서 일어나는 일:**
1. 플래너가 외부로 나가 필요 정보 확보 (인터뷰·자료 조사·데이터 확인)
2. 같은 대화창으로 돌아와 Claude에게 결과 공유
3. Claude가 반영해 문서 업데이트
4. 다시 Go/Kill/Hold 판정

**Hold 상한 2회인 이유:**
두 번 외부 정보 가져와도 결정 못 하면, 그 아이디어는 근본적으로 검증 불가능하거나 가치가 불명확하다는 증거다. 3회째 자동 Kill.

## 도구 환경

**기본 환경: Claude Projects.** A-0·A-1·A-2·A-3a·A-3b·B-1·B-2 일곱 핵심 문서 전부 Projects에서 작성. 이유는 외부 리서치(웹 검색, Research)가 Projects에서 자연스럽게 통합되기 때문. A단계는 외부 탐색 + 대화 왕복이 핵심이고, 이건 Projects의 강점이다.

**Claude Code는 Phase B 전용.** 개발·빌드 단계에서 로컬 파일을 다룰 때 쓴다. A단계에서 Claude Code로 빠져나갔다 돌아오는 하이브리드는 전환 비용이 더 크다. Projects에 맡기고 플래너는 병렬로 다른 일을 하는 게 더 빠르다.

**Skills 도입은 보류.** 3개 핵심 문서 체제가 안정화된 뒤 재포장 시점에 고려.

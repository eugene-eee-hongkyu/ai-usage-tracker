# 02 A-1 문서를 프로세스로 v3

> 00 기획 하네스 정책 v11을 토대로 한다. 작성 전 정책 문서의 "안 읽힘 6원인"·"문장 원칙"·"AI의 역할"·"번들링"·"턴 카운팅"을 참조한다.

---

## 이 문서 사용법

A-1는 **하네스의 두 번째 문서**이다. A-0에서 Go 판정을 받은 러프 유즈케이스 메인 라인을 **개발 가능한 프로세스**로 분해한다. "문서를 프로세스로" 옮긴다는 뜻이다.

이 문서에는 두 가지가 같이 들어 있다:
1. **산출물 템플릿** — A-1 산출물이 최종적으로 어떤 형태여야 하는가
2. **워크플로우** — Claude와 플래너가 어떤 순서로 채워가는가

Claude는 이 문서와 기획 하네스 정책 v11을 함께 읽은 뒤 A-1 작성을 시작한다.

A-0의 산출물(핵심 가설·메인 라인·MVP 경계 3개)이 A-1의 입력이다. A-0 없이 A-1 진입은 불가능.

---

## 산출물 형태 (A4 2~3장 목표)

> **분량 구분**
> - **이 문서 (템플릿+워크플로우)**: 분량 제한 없음. 작성 가이드다.
> - **A-1 산출물**: A4 2~3장 목표. 플래너가 실제로 만드는 문서.
>
> A-1는 유즈케이스 분해가 목적이라 A-0보다 분량이 자연히 늘어난다. 1장은 Phase별 Step을 못 담기에 무리. 3장 넘으면 한 번에 리뷰 어려움. 2~3장이 Phase 분해의 자연 크기다.

### 산출물 구조

A-1 산출물의 최종 형태는 아래 6개 섹션으로 구성된다.

```
[맨 앞] 1차 독자 선언문 (정책 규격)

1. A-0 요약 블록 (핵심 가설 + 메인 라인 + MVP 경계)
2. Phase 구조 개요 (Phase 3~5개 명명 + 각 1줄 설명)
3. Phase별 Step 상세 (Phase당 3~5 Step, 사용자 행동 + 시스템 행동)
4. 머릿속 시뮬레이션 체크 (주요 시나리오 2~3개)
5. 플래너 결정 필요 항목 ([SO 결정 필요] 마커로 표시)
6. Kill / Go / Hold 판정

[맨 끝] Claude의 적대적 압박 — "Kill할 이유 세 가지"
```

---

### 섹션별 상세

**1. A-0 요약 블록**

A-0 산출물의 핵심 3개를 맨 앞에 그대로 가져온다. A-1 전체가 이 3개를 기준으로 분해된다는 걸 시각적으로 강제.

- 핵심 가설 한 문장
- 러프 유즈케이스 메인 라인 3~5줄
- MVP 경계 3개 (제품·타겟·목표 행동)

**왜 필요한가:** A-1 작업 중에 플래너와 Claude 둘 다 핵심 가설을 자주 잊는다. 상단에 고정해두면 "이 Step이 핵심 가설 검증에 진짜 기여하는가"를 매번 대조 가능.

**2. Phase 구조 개요**

메인 라인을 3~5개 Phase로 쪼갠다. 각 Phase는 1줄로 명명 + 1줄로 설명.

- 형식: "P0. [Phase 이름] — [한 줄 설명]"
- 좋은 예:
  ```
  P0. 진입 & 재료 수집 — 사용자가 링크 접속해 해석 재료(생시·고민·반복 패턴)를 입력
  P1. 긴 해석 응답 — AI가 유명 역술가 톤으로 5~8문장 구체 해석 제공
  P2. 사용자 주도 Q&A (최대 3회) — 사용자가 궁금한 거 자유 질문, AI 답변, 입력창 상태 관리
  P3. 정리 & 저장 & 조건부 요청 — 정리 응답 + DB 저장 + (몰입 피크 시) 부모 생시 요청
  ```
- 나쁜 예: "P0. 입력" (너무 추상적, 뭘 하는지 안 드러남)

**Phase 개수 가이드:**
- 3개 미만이면 분해가 덜 된 것 → Step 다시 보고 쪼갤 것
- 5개 넘으면 MVP 경계를 넘어선 것 → 일부는 다음 버전으로 미룰 것

**3. Phase별 Step 상세**

각 Phase를 3~5개 Step으로 분해. Step 하나하나는 **사용자 행동 + 시스템 행동**을 짝으로 적는다. 한쪽만 있으면 모호함.

- 형식:
  ```
  **S[N]. [Step 이름]**
  사용자: [사용자가 하는 행동 — 화면·입력·탭 수준으로 구체]
  시스템: [AI·DB·UI가 하는 행동 — 무엇이 뒤에서 돌아가는지]
  ```
- 좋은 예:
  ```
  S4. 반복 패턴 4지선다
  사용자: 영역별 맞춤 4지선다 중 하나 탭 (예: 이직 고민 → "A. 잘 되다가 갑자기 그만두고 싶어짐")
  시스템: 선택값을 LLM 프롬프트에 재료로 투입 준비. 다음 스텝에서 긴 해석 생성 시 사용.
  ```
- 나쁜 예:
  ```
  S4. 질문
  사용자: 답함
  시스템: 처리
  ```
  (구체성 없음. 뭘 묻고 뭘 처리하는지 모름)

**Step 개수 가이드:**
- Phase당 3개 미만이면 Phase 경계가 너무 넓음
- Phase당 5개 넘으면 Phase 경계를 더 쪼개야 함

**4. 머릿속 시뮬레이션 체크**

완성된 Phase·Step을 실제 사용자 눈으로 따라 흘려본다. 주요 시나리오 2~3개.

- 형식:
  ```
  **시나리오 N: [한 줄 제목]**
  "[1인칭 서술로 Step 흐름 따라가기]"
  
  → 막히는 지점: [있으면 여기 / 없으면 "자연스러움"]
  ```
- 좋은 예:
  ```
  시나리오 1: 이직 고민 여성 첫 방문
  "링크 받고 접속. 생년월일시 입력. '지금 어떤 고민이세요?' → 이직 한 줄 타이핑.
  4지선다 나옴 → A 탭. 5분간 긴 해석 읽음. '맞네...' 드는 순간.
  '더 궁금한 거 있으세요?' → 자유 입력으로 '지금 이직하는 게 맞아요?' 타이핑.
  답변 받음. 2번째 질문 또 씀. 3번째는 고민하다가 정리 받기 선택.
  → 정리 응답 받음. 부모 생시 요청 안 옴 (3번 질문 다 안 썼으므로)."
  
  → 막히는 지점: 없음. 자연스러움.
  ```

**왜 필요한가:** Phase·Step 표는 추상적이다. 머릿속 시뮬레이션에서 막히는 지점이 나오면 그게 **실제 구현에서 터질 버그**다. 2~3개 시나리오로 체크해 미리 잡는다.

**5. 플래너 결정 필요 항목 ([SO 결정 필요] 마커)**

작업 중 Claude가 확정할 수 없는 지점이 나온다. 기술 선택·UX 세부·비즈니스 규칙 등. 이런 지점은 **본문 Step 안에 `[SO 결정 필요]` 마커**로 표시하고, 섹션 5에 모아서 정리.

**[SO 결정 필요] 항목 작성 의무 (정책 v11 원칙 5 적용):**

[SO 결정 필요] 항목은 **반드시 옵션 2~4개 + Claude 추천 + 이유**로 작성한다. "플래너가 결정하세요"만 적고 끝내는 건 판단 회피, 정책 v11 원칙 5 위반.

다음 패턴은 금지:
- ❌ `[SO 결정 필요] 부모 생시 입력 폼 구조 — Eugene이 결정해주세요`
- ❌ `[SO 결정 필요] Eugene이 생각하신 거 있으면 알려주세요, 없으면 "초안 줘"`

다음 패턴은 필수:
- ✅ 옵션 A, 옵션 B (구체적 안, 장단점 포함) + Claude 추천 + 이유(핵심 가설과의 연결)

**형식:**
```
[SO 결정 필요] N: [한 줄 질문]
- 옵션 A: [구체 안] — 장점 / 단점
- 옵션 B: [구체 안] — 장점 / 단점
- Claude 추천: [A 또는 B]
- 이유: [핵심 가설과의 연결로 서술]
```
- 좋은 예:
  ```
  [SO 결정 필요] 1: 부모 생시 입력 폼 구조
  - 옵션 A: 두 분 모두 → 생년월일만 → 한 분만 → 모름 시 환경 질문 (4단계 fallback)
  - 옵션 B: 두 분 정보 한 번에 묻고 없으면 패스 (1단계)
  - Claude 추천: A
  - 이유: 몰입 피크에 도달한 사용자는 정보 제공 의지가 높음. 단계별 fallback이 데이터 품질을 올림. 핵심 가설의 "3번 질문 다 쓴 사용자 = 몰입 피크" 정의와 정합.
  ```

**6. Kill / Go / Hold 판정**

정책 규격대로 세 가지 중 하나. 근거 3줄.

- **Go** — A-2(화면 결정)로 진입. 근거 3줄.
- **Kill** — 여기서 종료. 근거 3줄. Kill은 성공이다.
- **Hold** — 외부 정보 확보 후 재판정. 무엇을 알아야 하는지 명시. 최대 2회.

---

### 산출물 마지막 (Claude의 적대적 압박)

A-0과 동일. Claude가 자동으로 맨 아래에 "지금 이 프로세스를 죽일 이유 세 가지" 첨부. A-1 단계의 Kill 이유는 A-0과 다르다 — 아이디어가 아니라 **프로세스 설계의 구조적 결함**을 찌른다.

예시:
- "Phase 2의 사용자 주도 Q&A가 실패하면 전체 가설 검증 불가능"
- "Step 간 상태 관리 복잡도가 MVP 크기 초과"
- "특정 Phase가 기술적으로 불가능하거나 비용이 너무 큼"

---

## 워크플로우 (채우는 순서)

A-1도 A-0과 같은 원칙이다 — **메인 라인 먼저, 그 위에 번들링**. 플래너 턴 상한 8턴, 70% 경고 6턴째.

### STEP 0: 시작 선언 및 A-0 산출물 확인

**플래너의 행동:**
- `A-1 시작` 선언 (Claude의 턴 카운터 개시)
- A-0 산출물 첨부하거나, A-0을 같은 대화창에서 이어서 진행 중이면 별도 첨부 불필요

**Claude의 행동:**
- 턴 카운팅 시작
- A-0 산출물의 핵심 가설·메인 라인·MVP 경계 3개를 확인
- 이 3개가 명확하지 않으면 A-1 진입 불가 → 플래너에게 "A-0 먼저 마무리 필요" 알림

### STEP 1: Phase 구조 개요 제시 (번들링)

정책 v11 역할 5 "번들링" 원칙 적용. 한 응답에 Phase 구조 전체를 제시하고 플래너가 한 번에 피드백한다.

**Claude의 행동:**
- A-0 메인 라인을 Phase 3~5개로 쪼갠 초안을 제시
- 각 Phase에 이름 + 1줄 설명 + Step 개수 예상
- Phase 경계가 모호한 지점은 옵션 A/B로 제시 + 추천 + 이유

**예시 응답 형식:**
```
[A-1 진행: 턴 1/8]

A-0 메인 라인을 Phase 4개로 쪼갠 초안입니다. 이 구조로 진행할지 먼저 확인해주세요.

---

P0. 진입 & 재료 수집 (예상 4 Step)
사용자가 링크 접속해 해석 재료를 입력

P1. 긴 해석 응답 (예상 2 Step)
AI가 역술가 톤으로 구체 해석 제공

P2. 사용자 주도 Q&A (예상 3 Step, 최대 3회 루프)
사용자 자유 질문 → AI 답변 → 입력 상태 관리

P3. 정리 & 저장 & 조건부 요청 (예상 3 Step)
정리 응답 + DB 저장 + 조건부 부모 생시 요청

---

대안 고민 지점:
- P2와 P3 사이 명확한가? 아니면 "사용자가 '이제 됐어요' 누르기"를 Phase 경계로 볼까? (Claude 추천: 현재 구조. P3은 정리 단계로 분리하는 게 Step 응집도 더 높음)
- P0에 '반복 패턴 4지선다' 포함할지, P1로 옮길지? (Claude 추천: P0 유지. 해석 재료 수집 일환)

---

이 Phase 구조로 갈까요? 수정·추가 있으신가요?
```

**플래너의 행동:**
- Phase 구조 확인 / 수정 지시
- 대안 지점에 한 번에 답변

### STEP 2: Phase별 Step 상세 + 머릿속 시뮬레이션 + [SO 결정] 번들링

정책 v11 역할 5 "번들링" + 원칙 5 "초안 떠넘기기 금지" 동시 적용.

**Claude의 행동:**
- 확정된 Phase 구조를 Step으로 상세 분해
- 각 Step에 사용자 행동 + 시스템 행동 짝으로 기술
- 작업 중 결정 필요 지점은 `[SO 결정 필요]` 마커로 본문에 표시
- 머릿속 시뮬레이션 2~3개 자동 생성
- [SO 결정 필요] 항목 모두 옵션 + 추천 + 이유로 번들링해 제시

**"초안 떠넘기기 금지":**
- ❌ "Phase별 Step 개수에 대한 Eugene의 생각이 있으시면 알려주세요"
- ✅ "P0 Step 4개 초안 제시. S1. 생시 입력 / S2. 고민 입력 / S3. 영역 판별(비가시) / S4. 반복 패턴 4지선다. Eugene이 수정할 곳 있으면 지적해주세요."

**플래너의 행동:**
- Step 상세에서 수정 지시
- [SO 결정 필요] 항목들에 한 번에 답변
- 머릿속 시뮬레이션의 막히는 지점 있으면 지적

### STEP 3: 전체 조립 + Kill할 이유 3개 자동 생성

**Claude의 행동 (필수):**
- STEP 2의 플래너 피드백 반영해 A-1 산출물 전체 클린 조립
- 맨 아래에 **"Kill할 이유 세 가지"** 자동 추가
- 이는 정책 역할 1(적대적 압박)의 의무
- A-1 단계의 Kill 이유는 **프로세스 구조 결함**을 찌름 (A-0과 다름)

### STEP 4: Claude 판정 제안 + 플래너 확정

**Claude의 행동:**
- STEP 3의 Kill 이유 3개 포함해 전체 맥락 검토
- Go / Kill / Hold 중 하나 **추천** + 근거 3줄
- 플래너에게 "이 판정으로 가시겠습니까?" 확인

**플래너의 행동:**
- Claude 추천대로 확정하거나 다른 판정으로 수정
- 수정 시 Claude가 근거 3줄을 해당 판정에 맞게 재작성

## 턴 관리 (정책 v11 카운팅 메커니즘)

A-1의 턴 상한은 **8턴**이다. 70% 경고는 **6턴째**.

Claude는 매 응답 맨 위에 `[A-1 진행: 턴 N/8]` 표시. 6턴째부터 ⚠️ 경고, 8턴째 🛑 상한 도달.

### 일반적인 턴 소비 예상 (번들링 적용)

A-1가 Go로 끝나는 건강한 흐름:

| 턴 | 플래너 메시지 | Claude 응답 |
| --- | --- | --- |
| 1 | `A-1 시작` + A-0 확정본 | Phase 구조 개요 + 대안 지점 번들 제시 |
| 2 | Phase 구조 확정·수정 | **번들**: Phase별 Step 상세 + 머릿속 시뮬레이션 + [SO 결정 필요] 목록 |
| 3 | Step 수정 + [SO 결정] 일괄 답변 | 반영본 + 남은 [SO 결정] 재정리 |
| 4 | 남은 결정 마무리 | 전체 조립 초안 + Kill 이유 3개 + 판정 추천 |
| 5~6 | 최종 리뷰·수정 지시 | 클린 최종본 |
| 7 | Go 판정 | 종료 + A-2 진입 안내 |

이보다 많이 쓰면 뭔가 막힌 것이다. 8턴 초과 시 Claude가 Kill 이유 3개 제시, 16턴 초과 시 강한 Kill 권고.

**A-0보다 3턴 많은 이유:** Phase·Step 분해는 A-0의 한 장보다 결정 항목이 많다. [SO 결정 필요] 항목도 평균 2~4개 나오기 때문에 번들링해도 여유 필요.

## STEP 0에서 STEP 4까지 Claude가 지키는 원칙 요약

정책 v11의 5가지 공통 작성 원칙과 6가지 AI 역할을 A-1에 적용하면:

**작성 중:**

- 예시 없는 추상 정의 금지 (원칙 3) — 모든 Step에 구체 사용자·시스템 행동
- 메타 정보 금지 (원칙 4) — 작성일·상태 블록 금지
- 선택형 Q&A + 초안 떠넘기기 금지 (원칙 5) — [SO 결정 필요] 항목은 옵션+추천+이유로
- 번들링 (역할 5) — STEP 1에 Phase 구조 한 번에, STEP 2에 Step 상세+시뮬레이션+[SO 결정] 한 번에

**전달 직전:**
- 안 읽힘 탐지기 9항목 자체 점검 (역할 3)
- "Kill할 이유 3개" 필수 첨부 (역할 1)

**수정 시:**
- 지적받은 곳만 수정 (역할 4)
- 변경 가시화 (역할 6) — 수정된 섹션에 🔄 마크

## A-1에서 흔한 실패 모드

**실패 1: Phase 경계가 모호**
- 예: "P1: 해석 / P2: 대화"
- 왜 나쁜가: 어디서 P1 끝나고 P2 시작인지 모름. 구현 시 버그
- 교정: 각 Phase 시작·종료 트리거를 Step 수준으로 명시

**실패 2: Step에 사용자·시스템 둘 중 하나만 있음**
- 예: "S5. 질문 답변 받기" (누가 받는지, 뒤에서 뭐가 돌아가는지 없음)
- 왜 나쁜가: 구현자가 해석하게 됨. A-2에서 화면 설계 불가능
- 교정: 모든 Step에 사용자 행동 + 시스템 행동 짝으로

**실패 3: Step이 너무 잘게 쪼개짐**
- 예: "S1. 이름 입력칸 보기 / S2. 이름 클릭 / S3. 이름 타이핑 / S4. 이름 확인"
- 왜 나쁜가: 마이크로 상호작용은 A-2(화면 결정)의 영역. A-1는 기능 단위
- 교정: 하나의 사용자 의도가 완료될 때까지를 한 Step으로

**실패 4: 머릿속 시뮬레이션 생략**
- 왜 나쁜가: 표만 보면 자연스러워 보이지만 실제로 따라가면 막히는 지점이 드러남
- 교정: 주요 시나리오 2~3개 반드시 실행

**실패 5: [SO 결정 필요] 누락**
- 예: Claude가 기술·UX 세부를 혼자 결정해 박음
- 왜 나쁜가: 플래너가 나중에 발견. 재작업 비용 큼
- 교정: 모호하거나 Claude 재량을 넘어선 지점은 반드시 `[SO 결정 필요]` 마커

**실패 6: A-0 요약 블록 없음**
- 왜 나쁜가: A-1 작업 중 핵심 가설 잊음. Step이 가설 검증에서 멀어짐
- 교정: 산출물 맨 앞에 A-0 요약 3개 고정

## A-2 진입 조건 (Go 판정 시)

A-1가 Go로 끝나면 **A-2 (화면 결정)**로 진입한다. A-2에 넘길 것:

- 확정된 Phase 구조 개요 (3~5개)
- 확정된 Phase별 Step 상세
- 머릿속 시뮬레이션 통과 기록
- 해결된 [SO 결정 필요] 목록 (각 결정의 최종 선택)

A-2은 이 Step들을 **실제 화면**으로 매핑하는 작업이다. 어떤 Step이 한 화면에 합쳐지고, 어떤 Step이 여러 화면으로 쪼개지는지 결정.

# 03 A-2 프로세스를 화면으로 v4

> 00 기획 하네스 정책 v15를 토대로 한다. 작성 전 정책 문서의 "안 읽힘 6원인"·"문장 원칙"·"AI의 역할"·"번들링"·"변경 가시화"·"턴 카운팅"을 참조한다.

---

## 이 문서 사용법

A-2는 **하네스의 세 번째이자 마지막 핵심 문서**이다. A-1에서 Go 판정을 받은 Phase·Step 구조를 **실제 화면 설계**로 변환한다. "프로세스를 화면으로" 옮긴다는 뜻이다.

이 문서에는 두 가지가 같이 들어 있다:
1. **산출물 템플릿** — A-2 산출물이 최종적으로 어떤 형태여야 하는가
2. **워크플로우** — Claude와 플래너가 어떤 순서로 채워가는가

Claude는 이 문서와 기획 하네스 정책 v15를 함께 읽은 뒤 A-2 작성을 시작한다.

A-1의 산출물(Phase 구조·Step 상세·머릿속 시뮬레이션 결과·[SO 결정] 해결 내용)이 A-2의 입력이다. A-1 없이 A-2 진입은 불가능.

A-2가 Go로 끝나면 빌드 단계(Claude Code, Lovable 등)로 넘어간다. A-2 산출물이 빌드 도구의 **확정 스펙**이 된다.

---

## 산출물 형태 (분량 제한 없음)

> **분량 구분**
> - **이 문서 (템플릿+워크플로우)**: 분량 제한 없음. 작성 가이드다.
> - **A-2 산출물**: 분량 제한 없음. 필요한 만큼.
>
> A-2는 화면 설계가 확정 스펙으로 박혀야 하는 단계다. A-0(1장) · A-1(2~3장)과 달리 인위적 상한 두지 않는다. UX 의도를 충실히 담기 위해 필요한 만큼 쓴다. 다만 UI 세부(색·폰트·픽셀)는 빌드 도구 AI에게 맡기므로 그 부분은 기술하지 않는다.

### 산출물 구조

A-2 산출물의 최종 형태는 아래 7개 섹션으로 구성된다. **섹션 0(사람용 요약)은 v3에서 신설**된 항목으로, 사람이 빠르게 훑을 수 있게 맨 앞에 둔다.

```
[맨 앞] 1차 독자 선언문 (정책 규격)

0. 사람용 요약 (1~2 페이지, v3 신설)
   - 화면 흐름도 (ASCII Wireflow만, 전체 한 장에)
   - 주요 내부 로직 핵심 (각 항목 1줄)
   - 화면 목록 (이름 + 역할 1줄)

1. A-1 요약 블록 (A-0 핵심 가설 + A-1 Phase 구조)
2. 화면 목록 (화면 5~12개: 이름 + 포함 Step + 한 줄 목적)
3. 화면 간 전환 흐름 (Phase별 ASCII Wireflow)
4. 화면별 상세 스펙 (모든 화면)
   4-a. ASCII 와이어프레임 (실제 레이아웃)
   4-b. UX 의도 (왜 이런 경험인가)
   4-c. 인터랙션 (뭘 하면 뭐가 일어나는가)
   4-d. 상태 (로딩·에러·빈 상태 등)
5. 플래너 결정 필요 항목 ([SO 결정 필요] 마커)
6. Kill / Go / Hold 판정

[맨 끝] Claude의 적대적 압박 — "Kill할 이유 세 가지"
```

**0번이 사람 1차 독자, 1~6번이 AI(빌드 도구) 1차 독자.** 같은 파일 안에 두 형식이 공존. 분리 파일이면 동기화 깨짐 위험. 단일 파일이면 AI가 갱신 시 양쪽 모두 한 번에.

---

### 섹션별 상세

**0. 사람용 요약 (v3 신설)**

플래너가 A-2 산출물을 열면 **이 섹션만 보고도 전체 구조를 5분 안에 파악**할 수 있어야 한다. AI는 4-a/b/c/d를 읽지만 사람은 그 사이 사이의 글이 너무 많아 못 읽는다 — Eugene 사주톡 실전에서 발견된 문제. 이 섹션이 그 갭을 메운다.

**0-a. 화면 흐름도 (전체 한 장 ASCII Wireflow)**

화면 8~12개를 한 ASCII Wireflow에 다 담는다. 미니 박스 형식 — 화면 이름 + 핵심 요소 2~3줄 + 주요 버튼 + 화살표.

목적: 사람이 한눈에 "어떤 화면이 어떤 화면으로 이어지는가" 파악.

차이점:
- 섹션 3의 Wireflow: Phase별로 쪼갬 (자세히 봄)
- 섹션 0-a의 Wireflow: 전체 한 장 (한눈에 봄)

**0-b. 주요 내부 로직 핵심 (각 항목 1줄)**

화면에 안 보이지만 시스템이 뒤에서 하는 핵심 동작. AI 호출, 카운터 차감, DB 저장, 분기 로직 등.

좋은 예시 (사주톡):
```
- 만세력 계산: 생시 입력 → 천간·지지·십성 자동 계산
- 고민 영역 자동 분류: LLM이 텍스트를 이직/연애/결혼/기타로 분류
- 질문 카운터: 3 → 2 → 1 → 0, 0 도달 시 자동 정리 응답으로
- 4지선다 답 활용: 정리 응답 + DB 누적 둘 다 사용
- 부모 생시 조건부 요청: 3번 질문 다 쓴 사용자에게만 노출
```

각 줄이 짧다. 추상 표현 금지 — "사용자 친화적 흐름" 같은 것 안 됨. **한 동작 = 한 줄.**

**0-c. 화면 목록 (이름 + 역할 1줄)**

각 화면을 한 줄로 정리. 와이어프레임 없이 이름·역할만.

좋은 예시:
```
화면 1. 생시 입력 — 첫 세션 진입, 생년월일·성별·시간 입력
화면 2. 고민 입력 — 한 줄~두 줄로 고민 텍스트 입력
화면 3. 4지선다 — 영역별 맞춤 반복 패턴 질문
화면 4. 긴 해석 응답 — 5~8문장 스트리밍, 입력창 disabled
화면 5. 질문 프롬프트 — 입력창 활성, 카운터 노출
화면 6. 질문 답변 — AI 답변 스트리밍, 카운터 차감
화면 7. 정리 응답 — 대화 핵심 묶은 응답
화면 8. 부모 생시 요청 — 3번 다 쓴 사용자만 (조건부)
```

목적: 화면 개수 + 흐름 한눈에. 자세한 와이어프레임은 섹션 4에서.

**섹션 0의 핵심 원칙:**
- **분량 1~2 페이지 한도**. 넘으면 사람이 안 읽음.
- **사이 사이 글 최소화**. 다이어그램·목록·표 우선.
- **AI 시각으로 자세한 설명 안 들어감**. 그건 섹션 4의 역할.

**1. A-1 요약 블록**

A-1 산출물의 핵심을 맨 앞에 그대로 가져온다. 작업 중 플래너와 Claude 둘 다 원래 맥락을 자주 잊으므로 상단에 고정.

- A-0 핵심 가설 한 문장
- A-1 Phase 구조 개요 (Phase 3~5개 이름)
- MVP 경계 3개 (제품·타겟·목표 행동)

**왜 필요한가:** A-2 작업 중 "이 UX 결정이 핵심 가설 검증에 정말 기여하는가"를 매번 대조 가능.

**2. 화면 목록**

A-1의 Step들을 화면 단위로 재그룹화. 한 화면에 여러 Step이 들어갈 수도, 한 Step이 여러 화면으로 쪼개질 수도 있다.

- 형식: 각 화면에 번호·이름·포함 Step·한 줄 목적
- 예시:
  ```
  화면 1. 랜딩 (S1)
    링크로 접속한 사용자가 처음 보는 화면. 생시 입력 폼.
  
  화면 2. 고민 입력 (S2)
    생시 입력 완료 후 고민 한 줄 타이핑.
  
  화면 3. 반복 패턴 4지선다 (S3·S4)
    LLM이 고민 영역 분류한 뒤 맞춤 4지선다 표시.
  ```
- 화면 개수 가이드: 5~12개. 적으면 Step이 한 화면에 뭉쳐 복잡. 많으면 사용자 탐색 부담.

**3. 화면 간 전환 흐름 (Phase별 ASCII Wireflow)**

Nielsen Norman Group의 "wireflow" 포맷을 ASCII로 구현. 와이어프레임 + 플로우차트 결합. Phase 단위로 쪼개서 작성 (전체를 한 wireflow에 담으면 너무 커져서 못 읽음).

- 각 Phase당 별도 Wireflow
- 각 화면은 미니 박스: 이름 + 핵심 요소 2~4개 + 주요 버튼
- 화면 간 전환은 `─────▶` 화살표
- 조건부 분기는 `< 조건 텍스트 >` 마름모 대용
- 루프는 화살표가 뒤로 돌아감

**좋은 예시 (P0 Wireflow):**

```
┌──────────────┐      ┌──────────────┐
│ [S1] 생시입력│      │ [S2] 고민입력│
│ ·생년월일 ▢  │      │ ·텍스트 필드 │
│ ·시간 ▢(모름✓│─────▶│ ·placeholder │
│ ·성별 ▢      │      │ [다음]       │
│ [다음]       │      └──────┬───────┘
└──────────────┘             │
                             ▼
                    < 고민 영역? (LLM) >
                     │   │   │   │
                    이직 연애 결혼 기타
                     │   │   │   │
                     └─┬─┴───┴───┘
                       ▼
                ┌──────────────┐
                │ [S4] 4지선다 │
                │ ·영역별 질문 │
                │ ·선택지 A~D  │
                │ [A][B][C][D] │
                └──────┬───────┘
                       ▼
                   (P1 진입)
```

**나쁜 예시:**

```
화면1 → 화면2 → 화면3
```

이유: 버튼·필드·분기·루프가 안 보임. 플로우차트도 아니고 wireflow도 아닌 텍스트 나열.

**4. 화면별 상세 스펙 (모든 화면)**

섹션 4가 A-2의 핵심. 각 화면마다 4개 하위 섹션을 반드시 작성. 이중 하나라도 빠지면 빌드 단계에서 AI가 알아서 채우면서 **매번 다른 결과**가 나온다. A-2의 목적은 확정 스펙이다.

**4-a. ASCII 와이어프레임 (실제 레이아웃)**

화면 전체를 ASCII로 그린다. 섹션 3의 미니 박스보다 훨씬 상세. 실제 사용자가 보는 화면 비율에 가깝게.

원칙:
- ✅ 요소 **존재 여부**와 **배치** 명시 (있다/없다, 위쪽/아래쪽, 왼쪽/오른쪽)
- ❌ UI 시각 스타일 금지 (색·폰트·픽셀·border-radius 등). 빌드 도구 AI 영역.

**좋은 예시 (화면 4. 긴 해석 응답):**

```
┌─────────────────────────────────────┐
│ 사주톡              [질문 3번 남음]  │ ← 상단: 로고 + 카운터(우측)
├─────────────────────────────────────┤
│                                     │
│ 원국상 당신은 안정보다 성장을        │ ← 해석 본문 (5~8문장)
│ 중요하게 쓰는 타입입니다. 특히       │   스트리밍 표시
│ 이직 고민이 반복되는 건 [...]        │
│                                     │
│ (해석 스트리밍 중...)                │
│                                     │
├─────────────────────────────────────┤
│ 혹시 더 궁금한 거 있으세요?          │ ← 하단 프롬프트
│ ┌─────────────────────────────────┐ │
│ │ (입력창 — 해석 중 disabled)     │ │ ← 입력창 (비활성 상태)
│ └─────────────────────────────────┘ │
└─────────────────────────────────────┘
```

**나쁜 예시:**

```
해석 화면:
- 상단: 카운터
- 중앙: 해석 본문
- 하단: 입력창
```

이유: 배치 관계(상단/중앙/하단)는 있지만 **상대 크기·구조·실제 보이는 모습**이 없음. 빌드 AI가 "상단"을 어떻게 해석할지 매번 다름.

**4-b. UX 의도 (왜 이런 경험인가)**

이 화면이 왜 이렇게 설계됐는지. 핵심 가설과 어떻게 연결되는지. 각 주요 UX 결정마다 한 줄~두 줄.

**좋은 예시 (화면 4. 긴 해석 응답):**

```
- 질문 카운터 우측 상단 고정:
  사용자가 해석 읽는 내내 "아직 2번 더 쓸 수 있네"를 의식.
  핵심 가설("3번 다 씀") 검증 행동을 직접 유도.

- 입력창 disabled 유지:
  해석 스트리밍 중 중간에 질문 쓰고 싶어져도 막음.
  "긴 해석을 끝까지 읽어야 '내 얘기네' 체감"이 작동하는 구조.

- "혹시 더 궁금한 거" 프롬프트 하단:
  해석 완료 직후가 아니라 1~2초 여유 두고 노출. 읽은 내용
  소화 시간 제공. 즉시 노출되면 "생각 없이 그냥 닫기" 유도.
```

**나쁜 예시:**

```
사용자가 질문을 쓰도록 유도함.
```

이유: 너무 추상적. 왜 그 UX 선택을 했는지 연결 없음. 빌드 AI가 참조할 근거 없음.

**4-c. 인터랙션 (뭘 하면 뭐가 일어나는가)**

각 요소에 사용자가 뭘 하면 시스템이 뭘 하는지. 버튼 탭, 필드 입력, 화면 전환 등.

**좋은 예시 (화면 4):**

```
- 해석 스트리밍 완료 → 입력창 자동 enabled, "혹시 더 궁금한 거" 프롬프트 노출
- 사용자가 입력창에 타이핑 → 글자 표시
- 사용자가 전송 → 입력창 다시 disabled, 카운터 "2번 남음"으로 차감, 화면 5로 전환
- 카운터가 0 도달 시 사용자 전송 → 자동 화면 7(정리 응답)로 전환
```

**나쁜 예시:**

```
사용자가 질문 보내면 답변 나옴.
```

이유: 어떤 버튼·어떤 필드인지 불명확. 카운터 차감 같은 시스템 동작 누락.

**4-d. 상태 (로딩·에러·빈 상태)**

각 화면이 가질 수 있는 상태들. 정상 상태 외에 뭐가 더 있는가.

**좋은 예시 (화면 4):**

```
- 정상: 해석 본문 스트리밍 표시
- 로딩 초기: "해석 준비 중" 1~2초 (S5 배너에서 전환)
- 에러: "해석 생성 중 오류. 다시 시도하시겠어요?" + [재시도] 버튼
- 빈 상태: 없음 (이 화면은 항상 콘텐츠 있음)
```

**5. 플래너 결정 필요 항목 ([SO 결정 필요] 마커)**

작업 중 Claude가 확정할 수 없는 지점을 `[SO 결정 필요]` 마커로 본문에 표시하고, 섹션 5에 모아서 정리.

**[SO 결정 필요] 항목 작성 의무 (정책 v15 원칙 5 적용):**

A-1과 동일 규칙. 반드시 옵션 2~4개 + Claude 추천 + 이유.

다음 패턴은 금지:
- ❌ `[SO 결정 필요] 카운터 위치 — Eugene이 결정해주세요`

다음 패턴은 필수:
- ✅ 옵션 A, 옵션 B (구체적 안, 장단점 포함) + Claude 추천 + 이유

**형식:**

```
[SO 결정 필요] N: [한 줄 질문]
- 옵션 A: [구체 안] — 장점 / 단점
- 옵션 B: [구체 안] — 장점 / 단점
- Claude 추천: [A 또는 B]
- 이유: [핵심 가설 또는 UX 의도와의 연결]
```

**6. Kill / Go / Hold 판정**

정책 규격대로 세 가지 중 하나. 근거 3줄.

- **Go** — 빌드 단계(Claude Code, Lovable 등)로 진입. 근거 3줄.
- **Kill** — 여기서 종료. 근거 3줄. Kill은 성공이다.
- **Hold** — 외부 정보 확보 후 재판정. 무엇을 알아야 하는지 명시. 최대 2회.

### 산출물 마지막 (Claude의 적대적 압박)

A-0·A-1과 동일. Claude가 자동으로 맨 아래에 "지금 이 화면 설계를 죽일 이유 세 가지" 첨부. A-2 단계의 Kill 이유는 **UX 설계의 구조적 결함**을 찌른다 (A-0은 아이디어, A-1은 프로세스).

예시:
- "화면 4의 카운터 위치가 사용자 부담을 오히려 증가시킬 가능성"
- "화면 7(정리 응답) → 화면 8(부모 생시) 전환이 갑작스러워 이탈 위험"
- "화면 3의 4지선다가 '자유 질문'이라는 서비스 톤과 불일치"

## 워크플로우 (채우는 순서)

A-2도 A-0·A-1과 같은 원칙 — **메인 라인 먼저, 그 위에 번들링**. 플래너 턴 상한 10턴, 70% 경고 7턴째.

### STEP 0: 시작 선언 및 A-1 산출물 확인

**플래너의 행동:**
- `A-2 시작` 선언 (Claude의 턴 카운터 개시)
- A-1 산출물 첨부하거나, 같은 대화창에서 이어서 진행 중이면 별도 첨부 불필요

**Claude의 행동:**
- 턴 카운팅 시작
- A-1 산출물의 Phase 구조·Step 상세·[SO 결정] 해결 결과 확인
- A-1이 Go 판정으로 확정되지 않았으면 A-2 진입 불가 → 플래너에게 "A-1 먼저 마무리 필요" 알림

### STEP 1: 화면 목록 초안 제시 (번들링)

정책 v15 역할 5 "번들링" 원칙 적용. 한 응답에 화면 목록 전체를 제시하고 플래너가 한 번에 피드백한다.

**Claude의 행동:**
- A-1의 Step 13개(사주톡 예시)를 화면 단위로 재그룹화한 초안 제시
- 각 화면에 이름 + 포함 Step + 한 줄 목적
- 화면 경계가 모호한 지점은 옵션 A/B로 제시 + 추천 + 이유

**예시 응답 형식:**

```
[A-2 진행: 턴 1/10]

A-1 Step들을 화면 8개로 재그룹화한 초안입니다. 이 구성으로 진행할지 먼저 확인해주세요.

---

화면 1. 생시 입력 (S1)
화면 2. 고민 입력 (S2)
화면 3. 반복 패턴 4지선다 (S3·S4)
화면 4. 긴 해석 응답 (S5·S6·S7)
화면 5. 질문 프롬프트 (S7 이후 대기 상태)
화면 6. 질문 답변 (S8·S9·S10)
화면 7. 정리 응답 (S11·S12)
화면 8. 부모 생시 요청 (S13, 조건부)

---

대안 고민 지점:
- 화면 4에 S5(배너) + S6(해석) + S7(프롬프트)를 묶었는데, S5는 별도 화면으로 분리하는 게 나을까? (Claude 추천: 묶기. 배너가 짧아서 화면 전환 체감 없음)
- 화면 5와 6을 한 화면으로 묶을까? (Claude 추천: 분리. 대기 상태와 답변 상태는 UX 의도가 다름)

이 화면 구성으로 갈까요? 수정·추가 있으신가요?
```

**플래너의 행동:**
- 화면 목록 확인 / 수정 지시
- 대안 지점에 한 번에 답변

### STEP 2: Phase별 Wireflow 제시 (번들링)

**Claude의 행동:**
- 확정된 화면 목록을 Phase 단위로 쪼개 ASCII Wireflow 작성
- P0·P1·P2·P3 각각 별도 Wireflow
- 미니 박스 형식 (화면 이름 + 핵심 요소 2~4개 + 주요 버튼)
- 분기·루프는 화살표와 `<조건>` 마름모로 표현

**플래너의 행동:**
- Wireflow에서 전환 경로가 틀린 지점 지적
- 빠진 화면·분기 지적
- 확정 / 수정 지시

### STEP 3: 화면별 상세 스펙 번들 제시

정책 v15 역할 5 "번들링" + 원칙 5 "초안 떠넘기기 금지" 동시 적용.

**Claude의 행동:**
- 모든 화면의 4-a(ASCII 와이어프레임) + 4-b(UX 의도) + 4-c(인터랙션) + 4-d(상태)를 **한 응답에 묶어** 제시
- 분량이 많으면 2~3개 응답으로 쪼갤 수 있음. 단 "이번 응답은 화면 1~3, 다음 응답에 화면 4~6" 식으로 명확히 알림
- 작업 중 결정 필요 지점은 `[SO 결정 필요]` 마커로 본문에 표시
- [SO 결정 필요] 항목은 반드시 옵션 + 추천 + 이유

**"초안 떠넘기기 금지" 구체 예시:**

- ❌ "화면 4의 카운터 위치는 Eugene이 결정해주세요"
- ✅ "화면 4 카운터 위치 — 옵션 A: 우측 상단 / 옵션 B: 하단 고정. Claude 추천: A, 이유: F패턴 스캔에서 우측 상단이 먼저 보여 '아직 질문 가능' 자각 유도"

**플래너의 행동:**
- 화면별 상세에서 수정 지시
- [SO 결정 필요] 항목들에 한 번에 답변
- 빠진 UX 의도·인터랙션 지적

### STEP 4: 전체 조립 + 섹션 0 자동 생성 + Kill할 이유 3개

**Claude의 행동 (필수):**
- STEP 3의 플래너 피드백 반영해 A-2 산출물 전체 클린 조립
- **섹션 0 (사람용 요약) 자동 생성** — 섹션 1~6 작성 끝낸 뒤, 그 내용에서 추출:
  - 0-a. 화면 전체를 한 ASCII Wireflow에 압축 (Phase별 쪼개기 안 함)
  - 0-b. 시스템 동작에서 핵심 로직 추출, 각 1줄로
  - 0-c. 화면 목록 단순화 (이름 + 역할 1줄)
- 맨 아래에 **"Kill할 이유 세 가지"** 자동 추가
- 이는 정책 역할 1(적대적 압박)의 의무
- A-2 단계의 Kill 이유는 **UX 설계의 구조적 결함**을 찌름

### STEP 5: Claude 판정 제안 + 플래너 확정

**Claude의 행동:**
- STEP 4의 Kill 이유 3개 포함해 전체 맥락 검토
- Go / Kill / Hold 중 하나 **추천** + 근거 3줄
- 플래너에게 "이 판정으로 가시겠습니까?" 확인

**플래너의 행동:**
- Claude 추천대로 확정하거나 다른 판정으로 수정
- 수정 시 Claude가 근거 3줄을 해당 판정에 맞게 재작성

**Go 확정 시:**
- Claude가 **자동으로** 산출물 파일 저장 (정책 v15 역할 7)
- 파일명: `03_A-2_프로세스를_화면으로_[프로젝트명].md`
- 저장 위치: `/mnt/user-data/outputs/`
- 이 파일이 빌드 단계(Claude Code·Lovable)의 확정 스펙 입력

### 일반적인 턴 소비 예상 (번들링 적용)

A-2가 Go로 끝나는 건강한 흐름:

| 턴 | 플래너 메시지 | Claude 응답 |
| --- | --- | --- |
| 1 | `A-2 시작` + A-1 확정본 | 화면 목록 초안 + 대안 지점 번들 제시 |

## A-2에서 흔한 실패 모드

**실패 1: 화면 목록이 Step 수와 1:1**

- 예: Step 13개 → 화면 13개
- 왜 나쁜가: A-1 Step은 논리 단위, A-2 화면은 사용자 인지 단위. 다르다. 13개 화면은 전환 부담 큼
- 교정: 관련 Step 묶어서 5~12개 화면으로

**실패 2: ASCII 와이어프레임에 UI 스타일 침범**

- 예: `│ 카운터 (18pt 회색 우측 패딩 16px) │`
- 왜 나쁜가: UI는 빌드 도구 AI 영역. 플래너가 여기서 결정하면 하네스 철학 위반
- 교정: 요소 존재·배치만. 스타일은 금지

**실패 3: UX 의도가 "사용자 경험을 좋게 만듦" 수준으로 추상**

- 예: "이 화면은 사용자를 편하게 한다"
- 왜 나쁜가: 왜 그 선택인지 추적 불가. 핵심 가설과 연결 없음
- 교정: "[구체 UX 결정] → [구체 행동 효과] → [핵심 가설 기여]" 구조로

**실패 4: 인터랙션에서 시스템 동작 누락**

- 예: "버튼 누르면 다음 화면으로"
- 왜 나쁜가: 화면 전환은 사용자 보이는 부분만. 카운터 차감·DB 저장 같은 시스템 동작이 빠지면 빌드 AI가 놓침
- 교정: 사용자 행동 + 시스템 동작 짝으로

**실패 5: 상태 누락 (로딩·에러만 생각)**

- 예: 정상 상태만 기술. 에러·빈 상태 안 씀
- 왜 나쁜가: 빌드 AI가 디폴트로 채우면서 매번 다른 결과
- 교정: 정상·로딩·에러·빈 상태 체크 (없으면 "없음"이라고 명시)

**실패 6: 섹션 3 Wireflow가 전체 화면을 한 장에 담으려 함**

- 예: 섹션 3에 P0~P3 전체를 한 wireflow에
- 왜 나쁜가: 섹션 3은 자세히 보는 용도. 12개 화면이면 세로로 한없이 길어져 한 번에 못 봄
- 교정: 섹션 3은 Phase 단위로 쪼갬. 각 wireflow는 2~4개 화면만
- **주의**: 섹션 0-a(사람용 요약)는 정반대 — 전체 한 장이 의도. 두 섹션 목적이 다름.

**실패 7: [SO 결정 필요] 옵션 없이 질문만**

- 예: `[SO 결정 필요] 카운터 어디에 둘까요?`
- 왜 나쁜가: 플래너에게 떠넘기기. 원칙 5 위반
- 교정: 옵션 A/B + Claude 추천 + 이유

**실패 8: 섹션 0(사람용 요약)을 AI용 상세의 단순 복사로 만듦 (v3 신설)**

- 예: 섹션 0-a에 섹션 3 wireflow를 그대로 복붙
- 왜 나쁜가: 섹션 0은 1~2 페이지 압축이 목적. 단순 복사면 압축 안 된 거라 사람 못 읽음
- 교정: 섹션 0은 **재추출**해서 작성. 섹션 1~6 끝나고 그 내용에서 핵심만 추출.

**실패 9: 섹션 0 사이 사이 글이 많음 (v3 신설)**

- 예: 화면 목록 옆에 "이 화면은 사용자가 처음 접하는 곳으로 [...]" 같은 설명문
- 왜 나쁜가: 사람이 안 읽음. 섹션 0의 목적은 "한눈에 봄"
- 교정: 다이어그램·목록·표 우선. 설명문은 1줄까지만.

## A-2 갱신 (v3 신설, v4에서 이터레이션 추가)

A-2는 한 번 만들고 끝나는 문서가 아니다. 구현 진행 중·후에 **1~3회 갱신** 필요. 단 갱신 회수가 정해진 게 아니라 **트리거 기반**으로 갱신한다.

### 갱신 트리거 3개

다음 중 하나라도 발생하면 즉시 A-2 갱신:

1. **화면 추가/삭제** — 구현 중 화면 늘어나거나 합쳐짐
2. **화면 간 전환 변경** — Wireflow 자체가 바뀜 (예: 화면 X → Y가 X → Z로)
3. **핵심 가설 검증 결과 반영** — 사용자가 예상과 다르게 행동 → UX 의도 수정 필요

업계 최고 팀은 매 PR/커밋마다 자동 갱신(CI에 contract testing 통합). Eugene 같은 1인 개발자는 인프라 없으니 **트리거 기반 수동 갱신**이 현실적. 트리거 안 걸리면 갱신 안 함 — 회수 자체가 목적이 아님.

### 재작성 원칙 (갱신 방식)

**"갱신해"가 아니라 "코드 read하고 처음부터 작성해".**

이유: 코드는 거짓말 안 한다 (실제 동작). 기존 문서는 거짓말 가능 (의도와 구현이 분리). AI가 코드 읽고 처음부터 작성하면 100% 일치.

**갱신 워크플로우:**

```
[A-2 갱신 시점 도달]

1. Claude Code 세션 시작
2. 프롬프트:
   "[프로젝트] 코드베이스를 read한 뒤 A-2 산출물을 처음부터 작성한다.
    기존 A-2 파일은 참조용으로만 본다 (이전 의도 추출).
    코드와 기존 A-2가 충돌하면 코드를 따른다.
    UX 의도는 코드에서 추론할 수 있는 것만 적고,
    추론 불가는 [SO 결정 필요]로 미룬다.
    
    출력 — A-2 v3 형식 그대로:
    - 섹션 0 (사람용 요약): 화면 흐름도 + 내부 로직 + 화면 목록
    - 섹션 1~6: AI용 상세 (4-a/b/c/d 풀스펙)"
3. 결과 받음
4. 차이점 검토 (기존 A-2 vs 새 A-2)
5. 의도가 바뀐 경우만 의도 추가 보완 (코드에서 추론 안 되는 부분)
6. 새 A-2를 산출물로 저장 (기존 파일 덮어쓰기)
```

이 방식이 작동하는 이유:
- 코드를 1차 source of truth로 둠
- AI가 처음부터 작성하니 drift 0
- 사람은 의도 보완에만 집중 (전체 작성 안 함)

**제약 한 가지:** AI가 코드에서 추론 못 하는 항목 = "왜 이렇게 했는가"의 의도. Claude가 이 부분은 [SO 결정 필요]로 미루고, 사람이 그 부분만 채움.

### 이터레이션 워크플로우 (v4 신설)

A-2 문서를 쓰고 바로 개발 들어갔을 때 — 개발 완료 시점에 A-2와 코드 사이 차이가 큰 경우. 한 번의 재작성으로 정렬 안 되면 이터레이션. **종료 기준이 명확해야 무한 반복 안 함.**

**검증 체크리스트 7개**

자동 검증 가능 (Claude Code가 실행):

1. **화면 1:1 매핑** — 코드의 모든 컴포넌트(화면)이 A-2에 등장하는가? 누락 없음.
2. **A-2 화면 모두 존재** — A-2의 모든 화면이 코드에 구현됐는가? 잉여 없음.
3. **라우트 일치** — A-2 화면 간 전환과 코드 라우터가 일치?
4. **인터랙션 일치 (§4-c)** — A-2의 이벤트 핸들러가 코드에 구현됐는가?
5. **상태 일치 (§4-d)** — A-2의 loading·error·empty가 코드에 구현됐는가?

사람 검증 (플래너가 실행):

6. **UX 의도 살아있음 (§4-b)** — A-2의 UX 의도가 코드에 시각/동작으로 구현됐는가?
7. **누락 의도 없음** — 코드는 있는데 A-2에 의도 없는 화면 있는가?

**이터레이션 패턴**

```
[이터레이션 N]

1. Claude Code: 코드 read → A-2 v(N) 재작성 (위 재작성 원칙대로)
2. Claude Code: 자동 체크리스트 1~5 실행 → PASS/FAIL 보고
3. 플래너: 사람 체크리스트 6~7 실행 (~10분)
4. 결과 분류:
   - 모두 PASS + 이전 차수와 동일 → 종료 (수렴)
   - FAIL 항목 있음 → 수정 지시 → 이터레이션 N+1

[수정 지시 형태]
- FAIL 1·2·3·4·5 → 코드 또는 A-2 수정 (어느 쪽이 진실인지 결정)
- FAIL 6·7 → A-2 §4-b에 의도 추가/보완
```

**종료 기준 (둘 중 하나)**

- **기준 X**: 모든 체크리스트 PASS + 두 번 연속 동일 (수렴 신호 — 더 이상 변경 없음)
- **기준 Y**: 새 A-2 vs 이전 A-2 = diff 0 + 자동 검증 100%

**보통 수렴 횟수**

| 차수 | 발견 차이 | 사람 시간 |
|---|---|---|
| 1차 | 화면 누락·추가 (구조적 차이) | ~10분 |
| 2차 | 인터랙션·상태 차이 | ~10분 |
| 3차 | UX 의도 미세 정렬 | ~10분 |
| 4차 | 보통 변경 없음 → 종료 | ~5분 |

**보통 2~3차에 수렴.** 사람 시간 합계 30~40분.

**3차 넘어가면 다른 신호:**

- A-2 형식 자체가 코드 구조와 안 맞음 → 템플릿 재검토
- 코드가 너무 자주 바뀜 → 갱신을 멈추고 코드 안정화 후 재시도
- 자동 체크리스트는 PASS인데 사람 체크리스트 계속 FAIL → A-2 §4-b 의도 자체가 모호함, A-1 회귀 필요

### 갱신 시점 vs Kill 시점

A-2 갱신을 너무 자주 한다고 느끼면 **다른 신호**일 수 있음:
- 같은 화면을 3번 이상 갱신 → 화면 자체가 잘못 설계됨, A-2 v(N)이 문제
- 갱신할 때마다 화면 늘어남 → MVP 경계 무너짐, A-0으로 회귀
- Wireflow가 자꾸 바뀜 → A-1 Phase 구조가 잘못됨

이 경우 갱신이 아니라 **이전 단계로 돌아가서 재정의** 필요.

## A-3 진입 조건 (Go 판정 시)

A-2가 Go로 끝나면 **A-3 (화면을 디자인으로)**로 진입한다. A-3에 넘길 것:

- A-2 산출물 파일 (정책 v15 역할 7에 따라 자동 저장)
- A-0·A-1 산출물 파일 (참조용)

A-3은 이 와이어프레임에 **시각 디자인**(톤·컬러·폰트·핵심 화면 디자인 의도)을 박는 단계다. 디자인 도구는 Claude Design (디폴트, claude.ai 내) 또는 Stitch (무료 대안).

**A-3 우회 — 명시적 결정일 때만:**
사내 도구·로컬 데모 등 디자인 무관한 MVP는 A-3 건너뛰고 B-1 직진 가능. 단 빌드 도구 디폴트 디자인이 적용됨을 알고 진행. 외부 사용자 대상 MVP는 A-3 권장.

## 이 문서 사용법

A-3b는 **하네스의 다섯 번째 핵심 문서**이다. A-3a에서 컨펌된 메인 화면 디자인(DESIGN.md)을 **나머지 모든 화면에 자동 적용**한다. 사람 디자이너 best case 4단계.

**A-3b의 정체성:**

A-3a가 컨셉 탐색이라면 A-3b는 적용. A-3a에서 메인 화면 1~2개 변형 비교 후 컨펌 → DESIGN.md 추출. 이제 그 DESIGN.md를 나머지 화면(A-2의 모든 화면 중 메인 외)에 자동 적용한다.

```
[A-3a 완료 시점]
  메인 화면 디자인 컨펌됨
  DESIGN.md 확정됨

[A-3b 시작]
  ↓
DESIGN.md + A-2 화면 목록 → 디자인 도구
  ↓
나머지 화면(메인 외) 자동 생성
  ↓
DESIGN.md 일관성 자동 보장
  ↓
handoff bundle 출력 (B-1 입력)
```

**왜 별도 단계인가:**

이전에 A-3 한 단계로 묶었을 때 단점 — 메인 디자인 컨펌과 전체 적용이 같은 Go 게이트로 묶임. 분리하면:
- A-3a Kill: 디자인 방향 자체 잘못 → A-2 회귀
- A-3b Kill: 메인은 좋은데 전체 적용 시 충돌 → A-3a 회귀 (메인 보완)

Kill 시 정확한 회귀 위치 명확.

또 다른 이유: 외부 작업 시간 차이 큼.
- A-3a: 메인 1~2개 변형 비교 (1~3시간)
- A-3b: 나머지 화면 자동 적용 (10~30분)

분리하면 각 단계별 시간 추정 명확.

### 2. 전체 적용 결과

**2-a. 화면별 디자인 적용 상태**

A-2 §4의 모든 화면을 표로 정리. 메인 화면(A-3a 컨펌)과 나머지(A-3b 자동 생성) 구분.

**좋은 예시 (사주톡):**
```
| 화면 | 단계 | 상태 | 비고 |
|---|---|---|---|
| 화면 1 (랜딩) | A-3b 자동 | OK | DESIGN.md 적용 완료 |
| 화면 2 (고민 입력) | A-3b 자동 | OK | - |
| 화면 3 (4지선다) | A-3b 자동 | OK | - |
| 화면 4 (긴 해석) | A-3a 컨펌 | OK | 메인 화면 |
| 화면 5 (질문 프롬프트) | A-3a 컨펌 | OK | 메인 화면 |
| 화면 6 (질문 답변) | A-3b 자동 | OK | 화면 5 시스템 따라 |
| 화면 7 (정리 응답) | A-3b 자동 | OK | - |
| 화면 8 (부모 생시) | A-3b 자동 | OK | 조건부 화면 |
```

**2-b. 일관성 체크**

DESIGN.md의 토큰(컬러·폰트·spacing)이 모든 화면에 동일하게 반영됐는지. 디자인 도구가 자동 보장하지만 검증 필수.

**검증 항목:**
- 컬러: Primary/Secondary/Accent가 모든 화면에서 동일 HEX
- 폰트: heading·body가 모든 화면에서 동일 (한글·영문 페어링 일관)
- spacing: sm/md/lg가 동일 px
- 컴포넌트 패턴: 버튼·입력창·카드 모양이 동일

**불일치 발견 시:** [SO 결정 필요]로 미루거나 디자인 도구에 재요청.

**2-c. UX 의도 보존 체크**

A-2 §4-b의 UX 의도가 시각으로 구현됐는지. 가장 중요한 검증.

**좋은 예시 (사주톡):**
```
화면 4 UX 의도 (A-2 §4-b):
- "질문 카운터 우측 상단 고정" → 골드 컬러로 구현 ✓
- "입력창 disabled 유지" → opacity 50% ✓
- "1~2초 여유 후 프롬프트 노출" → fade-in 1500ms ✓

화면 7 UX 의도 (A-2 §4-b):
- "대화 핵심 묶기" → 정리된 카드 레이아웃 ✓
- "다음 단계 자연 유도" → 부모 생시 요청 버튼 골드 강조 ✓

전체 일관성: ✓
```

**불일치 발견 시:** 해당 화면 디자인 도구에 재요청. UX 의도가 살아있어야 함.

### 3. handoff bundle 정보 (Claude Design 사용 시)

Claude Design이 자동 생성한 bundle ZIP의 구성. B-1에서 unzip해 적용할 때 필요.

**좋은 예시:**
```

├── DESIGN.md                        ← repo 루트로
```

**3-b. B-1에 적용할 위치 매핑**

```

styles/design-tokens.css → /sajutalk/styles/design-tokens.css
tailwind.config.additions.js → /sajutalk/tailwind.config.js (merge)
components/*.tsx → /sajutalk/app/components/ 또는 기존 위치
```

### 4. [SO 결정 필요] 항목

A-3b는 자동 단계라 [SO 결정] 거의 없지만 발생 시:
- 일관성 체크 실패 화면 → 어떻게 처리할지
- handoff bundle 적용 시 충돌 → 기존 코드 보존 vs 덮어쓰기

**A-3b에서 결정 많으면 신호:** A-3a 컨셉이 약함. A-3a 회귀 필요.

### 5. Kill / Go / Hold 판정

## A-3b 흔한 실패 모드

**실패 1: DESIGN.md 일관성 체크 표면적**
- 예: "PASS"라고만 적고 실제 토큰 비교 안 함
- 왜 나쁜가: 일관성 깨졌어도 발견 못 함, B-1에서 발견 → 재작업
- 교정: 컬러·폰트·spacing 항목별 명시적 검증

**실패 2: UX 의도 보존 체크 누락**
- 예: 시각만 보고 UX 의도 안 검증
- 왜 나쁜가: 디자인이 예쁘지만 UX 깨질 수 있음
- 교정: A-2 §4-b 항목별 시각 구현 확인

**실패 3: 메인 화면 자동 적용 시 변경**
- 예: 디자인 도구가 메인 화면도 미세 수정
- 왜 나쁜가: A-3a 컨펌 결과 깨짐
- 교정: 프롬프트에 "메인 화면(화면 4·5)는 그대로 유지" 명시

**실패 4: handoff bundle 적용 위치 매핑 누락**
- 예: bundle 파일만 있고 어디에 둘지 모름

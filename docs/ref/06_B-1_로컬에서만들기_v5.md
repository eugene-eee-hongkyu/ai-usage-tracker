# 06 B-1 로컬에서만들기 v5

> 00 기획 하네스 정책 v15을 토대로 한다. 작성 전 정책 문서의 "안 읽힘 6원인"·"문장 원칙"·"AI의 역할"·"번들링"·"변경 가시화"·"턴 카운팅"을 참조한다.

## 이 문서 사용법

B-1은 **하네스의 네 번째 핵심 문서**이다. A-2에서 Go 판정을 받은 화면 스펙을 **로컬 머신에서 Claude Code가 `--dangerously-skip-permissions` 모드로 헤매지 않고 실행할 수 있는 한 장짜리 빌드 지침서**로 변환한다.

**B-1의 정체성: 로컬 검증.**
- 인프라(Vercel·Supabase 등 SaaS) 배제. 로컬 머신에서만 실행.
- 시나리오 1·2 PASS가 1차 목표.
- 인프라로 올릴 때 구조 변경이 최소화되도록 **포터빌리티 체크리스트** 13개 자동 검증.

**B-2와의 분리:**
- B-1: 로컬 실행 + 시나리오 PASS + 포터빌리티 검증
- B-2: B-1 결과물을 인프라로 배포 (별개 산출물)

이 문서에는 두 가지가 같이 들어 있다:
1. **산출물 템플릿** — B-1 산출물이 최종적으로 어떤 형태여야 하는가
2. **워크플로우** — Claude와 플래너가 어떤 순서로 채워가는가

Claude는 이 문서와 기획 하네스 정책 v15을 함께 읽은 뒤 B-1 산출물 작성을 시작한다.

A-0/A-1/A-2/A-3a/A-3b 산출물이 B-1의 입력이다. 특히:
- **A-2** (화면 목록·Wireflow·화면별 4-a/b/c/d 상세 스펙) — 구조 입력
- **A-3a** (메인 화면 디자인 컨펌) — 컨셉 입력
- **A-3b** (전체 화면 적용 + handoff bundle) — 시각 입력
- **DESIGN.md** (Google 표준 형식) — repo 루트에 배치, AI 에이전트 자동 인식

A-3 없이 B-1 진입하면 디자인이 빌드 도구 디폴트로 채워져 타겟에 안 맞는 결과 나옴. A-3 우회는 명시적 결정일 때만 (예: 사내 도구라 디자인 무관).

B-1 산출물이 Go로 끝나면 Claude Code `--dangerously-skip-permissions` 세션으로 넘어간다. B-1 산출물이 그 세션의 **유일한 실행 지침서**가 된다.

## B-1 단계의 정체성

A 트랙이 "플래너 뇌에서 생각을 꺼내는 것"이었다면, B-1은 **"Claude Code가 혼자 결정하면 헤매거나 틀릴 지점을 플래너가 아닌 Claude(Projects)가 사전에 압축해두는 것"**이다.

이 정의는 두 가지를 함의한다:

**함의 1. B-1은 Claude 주도, 플래너는 결정 지점만 확인.**
A 트랙에서 플래너가 체계화를 리드했다면, B-1에서는 Claude가 A 산출물 읽고·웹 조사하고·스택 결정하고·초안 쓰는 게 디폴트다. 플래너는 "내 도메인 지식이 필요한 결정 지점"만 확인한다.

**함의 2. B-1 산출물의 1차 독자는 Claude Code다.**
A 산출물은 1차 독자가 플래너였다. B-1 산출물의 **1차 독자는 Claude Code**이다. 플래너는 §11(첫 프롬프트 복붙) §12(완료 보고) §6(LLM prompt 선택) 외에는 직접 읽지 않는다. 따라서 모든 섹션은 **Claude Code가 명확히 해석할 수 있도록** 작성. 추상 표현·완충어·암묵적 가정 금지.

**함의 3. 인프라 비종속 코드.**
B-1에서 짜는 모든 코드는 인프라로 올릴 때 구조를 바꾸지 않아야 한다. 12-Factor App 원칙 기반 13개 체크리스트로 자동 검증. 이 검증을 통과해야 B-2 진입 가능.

## 산출물 형태 (분량 제한 없음)

> **분량 구분**
> - **이 문서 (템플릿+워크플로우)**: 분량 제한 없음. 작성 가이드다.
> - **B-1 산출물**: 분량 제한 없음. AI가 읽고 구현할 문서다. 빠진 내용 없게 충실히. Claude Code 컨텍스트 윈도우에 들어갈 정도면 됨.

### 산출물 구조

B-1 산출물의 최종 형태는 아래 구조로 구성된다.

```
[맨 앞] 1차 독자 선언문 (1차 독자는 Claude Code, 플래너는 §1·§6·§7·§11·§12만 읽음)

0. A 트랙 요약 블록
   - A-0 핵심 가설
   - A-1 Phase 구조
   - A-2 화면 목록

1. 시작 전 체크리스트 (사람이 준비해야 할 것 — 로컬 한정)
2. 기술 스택 확정 + 1줄 이유 (로컬 우선, SaaS 금지)
3. 기술 리스크 사전 조사 (라이브러리 비교 + 추천 + Hold 플래그)
4. 프로젝트 구조 스켈레톤 (폴더·DB 스키마·환경변수)
5. 빌드 순서 (의존성 있는 순서)
6. LLM system prompt 초안 (복수, 플래너 선택용)
7. 플래너 결정 항목 ([SO 결정 필요] 마커)
8. Claude Code 재량 범위 (혼자 결정 OK 목록)
9. bypass 멈춤 트리거 (반드시 사람에게 물어야 할 것)
9.5. 실패·재시도 상한 (같은 실패 3회 룰 등)
10. 검증 방법 — 시나리오 PASS + 포터빌리티 13개 체크
11. Claude Code 첫 프롬프트 템플릿 (복붙 가능)
12. 완료 보고 포맷 (Claude Code가 세션 끝에 남길 것 — 13개 체크 포함)
13. Kill / Go / Hold 판정

[맨 끝] Claude의 적대적 압박 — "Kill할 이유 세 가지"
```

### 섹션별 상세

#### 0. A 트랙 요약 블록

A-0·A-1·A-2 산출물의 핵심을 맨 앞에 고정. Claude Code 세션 중간에 "지금 뭘 만들고 있는 거였지"를 잊지 않도록.

- **A-0 핵심 가설 한 문장** (A-0 §1 그대로)
- **A-1 Phase 구조 개요** (P0~PN 이름 + 1줄 설명)
- **A-2 화면 목록** (화면 이름 나열, 번호·포함 Step만)
- **MVP 경계 3개** (제품·타겟·목표 행동)

#### 1. 시작 전 체크리스트

**플래너가 Claude Code 세션 시작 전에 반드시 완료해둬야 할 것.** 로컬 한정 — 인프라 서비스 계정 금지.

bypass 모드는 계정 생성·이메일 인증·유료 티어 결제를 대신할 수 없다.

체크박스 형식:
```
[ ] <서비스> 계정 생성
    → 필요한 것: <구체 key/토큰 이름>
    → 발급 위치: <URL>
[ ] <도구> 설치 확인
    → 확인 명령: <cmd>
```

**필수 포함 카테고리 (B-1 한정 — 로컬 인프라만):**
- LLM API key (Anthropic·OpenAI·Gemini 등) — 로컬에서 LLM 호출 위해 필수
- Repo 관리 (GitHub 등) — 코드 버전 관리, 인프라 의존 아님
- 로컬 DB 도구 (SQLite는 zero-config, Postgres는 Docker)
- Node.js·Python 등 런타임 설치 확인
- Claude Code 설치 확인

**B-1에서 금지된 카테고리 (B-2로 미룸):**
- Vercel·Netlify·Cloudflare 등 배포 서비스
- Supabase·Neon·PlanetScale 등 SaaS DB
- Stripe·Paddle 등 결제
- 도메인·DNS

**꼭 마지막에 "필요한 key 전체 목록"을 별도 블록으로** — Claude Code가 환경변수 파일 템플릿 생성할 때 이 목록을 그대로 쓴다.

**좋은 예시:**
```
[ ] Anthropic API key 발급 (console.anthropic.com)
    → 크레딧 최소 $10 충전 (MVP 검증용, 100회 호출 예상)
```

**나쁜 예시:**
```
[ ] LLM 계정 만들기
```
이유: 어느 서비스인지·어떤 key가 필요한지 명시 안 됨. Claude Code가 결국 물어봄.

#### 2. 기술 스택 확정 + 1줄 이유

Claude Code가 "Next.js냐 Remix냐" 고민하지 않도록 스택 전체를 박아둔다. **각 선택에 1줄 이유**를 붙여야 플래너가 나중에 "왜 이걸 골랐지" 재검토 가능.

**B-1 스택 결정 원칙:**
1. **로컬 우선** — SaaS 종속성 0개
2. **인프라로 옮길 때 어댑터만 갈아끼우면 되는 구조** (12-Factor 백업 서비스 원칙)
3. MVP 속도 (세팅 시간 짧을 것)
4. Claude Code가 이미 익숙한 패턴
5. 무료 티어로 MVP 범위 소화 가능 여부 (LLM API 외엔 무료)

**좋은 예시:**
```
| 영역 | 선택 | 1줄 이유 |
| --- | --- | --- |
| 프레임워크 | Next.js 14 App Router | 표준 스택 + AI SDK 스트리밍 지원 |
| DB (로컬) | SQLite (better-sqlite3) | zero-config, 파일 하나, B-2에서 Postgres로 어댑터 교체 |
| ORM | Drizzle | SQLite·Postgres 모두 지원, 인프라 전환 시 코드 무변경 |
| UI | shadcn/ui + Tailwind | 가볍고 디폴트 디자인 양호 |
| LLM SDK | @anthropic-ai/sdk | 인프라 무관, 환경변수만 |
```

**나쁜 예시:**
```
Next.js + Supabase 씁니다.
```
이유: Supabase는 SaaS. B-1에서 금지. B-2에서 결정.

#### 3. 기술 리스크 사전 조사

Claude Code가 혼자 라이브러리 조사하면 30분~1시간씩 날린다. Claude(Projects)가 **먼저 웹 검색해서 후보 비교표와 추천**을 남긴다.

**조사 깊이 — 층위 2 기본:**
- 후보 2~3개 나열
- 각 후보의 주간 다운로드·유지보수 상태·라이선스·API 형태
- 추천 1개 + 이유

**층위 3 (실제 코드 검증)은 예외적으로만.** 핵심 가설 검증에 직결되는 항목만.

**Hold 신호 조항:** 조사 결과가 "라이브러리가 X를 보장하는지 불명확" 같은 상태로 끝나면 **Hold 플래그**를 섹션 7(플래너 결정 항목)에 명시. 플래너가 샘플 1개로 수동 검증 후 Go.

**조사 대상 카테고리 (프로젝트별 다름):**
- 핵심 도메인 라이브러리 (사주톡의 만세력, 그림 그리기 앱의 캔버스 라이브러리 등)
- ORM·DB 어댑터 (12-Factor 백업 서비스 원칙 만족 여부 확인)
- 인증 라이브러리 (로컬·인프라 모두에서 작동하는지)
- LLM SDK·스트리밍 라이브러리

#### 4. 프로젝트 구조 스켈레톤

**폴더 레이아웃**: 주요 디렉토리와 용도. 12-Factor 원칙 반영.

**DB 스키마 개요**: 테이블·주요 컬럼 (정확한 SQL은 Claude Code가 생성)

**환경변수 목록**: `.env.local` 템플릿. **모든 외부 의존(DB·LLM·인증)은 환경변수로 추상화** — B-2에서 환경변수 값만 바꿔 인프라로 전환 가능해야 한다.

**좋은 예시 (폴더 구조 — 사주톡):**
```
sajutalk/
├── app/                       ← Next.js App Router
│   ├── api/
│   │   ├── session/
│   │   ├── interpret/
│   │   └── qna/
│   └── (screens)/
├── lib/
│   ├── db/                    ← DB 어댑터 (SQLite ↔ Postgres 교체 가능)
│   │   ├── index.ts           ← 환경변수로 분기
│   │   ├── sqlite.ts
│   │   └── postgres.ts
│   ├── llm/                   ← LLM 어댑터 (provider 교체 가능)
│   ├── prompts/               ← system prompt 모음
│   └── manse/                 ← 도메인 로직 (만세력)
├── data/                      ← 로컬 SQLite 파일 (gitignore)
├── styles/
│   └── design-tokens.css      ← A-3b handoff bundle에서 적용
├── tailwind.config.js         ← DESIGN.md의 토큰 적용
├── DESIGN.md                  ← repo 루트, AI 에이전트 자동 인식 (Google 표준)
├── figma.config.json          ← [트랙 A 전용] Code Connect 매핑
└── .env.local                 ← key 모음
```

**트랙 A·B 분기 (정책 v15):**
- 트랙 A (디자이너 있음): figma.config.json 추가 + Figma MCP 연결
- 트랙 B (디자이너 없음): figma.config.json 없음 + Figma MCP 연결 안 함

**A-3 디자인 적용 (필수):**

A-3b handoff bundle을 다음 위치에 적용:
- `DESIGN.md` → repo 루트 (Google 표준, Claude Code·Cursor·Stitch가 자동 인식)
- `styles/design-tokens.css` — CSS 변수 (DESIGN.md YAML에서 추출)
- `tailwind.config.js` — Tailwind 설정에 추가 (DESIGN.md 토큰 매핑)
- `app/layout.tsx` 또는 `_app.tsx` — `import './styles/design-tokens.css'` 추가
- 폰트: Google Fonts 링크를 `<head>`에 추가 (DESIGN.md `typography` 섹션에 명시된 폰트)
- `components/*.tsx` — handoff bundle의 컴포넌트 파일 적용

A-3b handoff bundle이 없으면(Stitch 만 사용한 경우) DESIGN.md만 받아 위 파일들을 Claude Code가 생성.

**환경변수 템플릿 좋은 예시 (.env.local):**
```bash
# LLM
ANTHROPIC_API_KEY=sk-...

# DB (로컬: sqlite, 인프라: postgres URL)
DATABASE_URL=sqlite:./data/saju.db
DATABASE_PROVIDER=sqlite

# 앱
PORT=3000
NODE_ENV=development
```

**Claude Code에게 주는 지시:** "위 스키마는 개요. 정확한 SQL migration과 마이그레이션 스크립트(`npm run migrate`)를 Claude Code가 생성. ORM(Drizzle)으로 SQLite·Postgres 호환 스키마 정의."

#### 5. 빌드 순서

**의존성 있는 순서**대로 단계 나열. Claude Code가 이 순서로 실행.

**좋은 예시 (사주톡):**
```
1. `npm create next-app sajutalk` → TypeScript·Tailwind·App Router 선택
2. `npx shadcn init` + 필요 컴포넌트 설치 (button, input, card)
3. .env.local 생성 + 섹션 1 key 목록 채우기
4. **A-3 디자인 토큰 적용** (styles/design-tokens.css + tailwind.config.js + 폰트 link)
4.5. **CLAUDE.md 자동 머지** (정책 v15 §표준 형식 채택)
   - 기존 CLAUDE.md 존재 확인
   - 없음: 새로 생성 (Project Overview·Coding Conventions·Build Standards·Halt Triggers 섹션)
   - 있음: 새 섹션만 append, 충돌만 사용자 1회 확인, 백업 자동
4.6. **SPEC.md 생성** (B-1 산출물 §0~§9 요약)
   - repo 루트에 생성
   - Claude Code·Cursor 자동 인식
4.7. **DESIGN.md 검증** (Google 스펙 준수)
   - A-3a/A-3b에서 만든 DESIGN.md가 repo 루트에 있는지 확인
   - YAML 프론트매터 + Markdown 본문 형식 검증
```

#### 6. LLM system prompt 초안 (복수)

이 섹션은 **플래너가 선택해야 하는 것**. PART 1에 있다.

A 트랙에서 안 다뤘던 영역. LLM 내부 지침은 화면에 안 보이지만 검증 축(예: "내 얘기네" 체감)에 결정적이다. Claude가 복수 초안 쓰고 플래너가 섹션 7에서 선택.

**원칙:**
- 2~3개 초안 제시 (톤이 서로 구분되게)
- 각 초안에 "언제 이게 맞는가" 한 줄
- Claude 추천 + 이유

**예시 구조 (톤만. 내용은 프로젝트별):**
```
초안 A: [톤 이름]
...prompt 본문...

초안 B: [톤 이름]
...prompt 본문...

초안 C: [톤 이름]
...prompt 본문...

Claude 추천: <A|B|C>
이유:
1. A-0 ___ 명시됨
2. ___가 핵심 가설 ___와 직결
3. ___
```

**초안 수: 2~3개.** 1개면 선택이 아님. 4개 넘으면 플래너 부담.

**프로젝트에 prompt가 여러 개 필요하면** (예: 긴 해석·Q&A·정리 3개), 각각 섹션 6-a, 6-b, 6-c로 나눠서 각각 복수 초안.

#### 10. 검증 방법 — 시나리오 PASS + 포터빌리티 13개 체크

**B-1의 검증은 두 단계:**

**단계 1. 시나리오 PASS (A-1 §4 시나리오를 localhost에서 E2E로)**

A-1 §4 시나리오를 E2E로 통과시킨다.

형식:
```
[검증 1] A-1 시나리오 1: <한 줄 요약>
  실행 방법: <수동 / Playwright 자동>
  PASS 조건: <구체적 관찰 항목>
  - 관찰 1: ___
  - 관찰 2: ___
  - 관찰 3: ___

[검증 2] A-1 시나리오 2: ...
```

**수동 vs Playwright 선택:**
- 시나리오에 사용자 타이핑이 많고 분기가 많으면 Playwright가 편함
- MVP 단계·시나리오 2~3개는 수동이 더 빠름
- **Claude 디폴트 추천: 수동**

**PASS 조건은 구체적으로.** "정상 작동" 같은 추상 금지.

**단계 2. 포터빌리티 13개 체크리스트 (12-Factor App 기반 + 서버리스 호환성 추가)**

**Claude Code가 빌드 끝에 자동 점검**. 각 항목 PASS/FAIL을 §12 완료 보고에 기록.

```
[1] 코드베이스 (1 codebase, many deploys)
    - 단일 git repo에서 로컬·인프라 모두 배포 가능?
    - 환경별 다른 코드 브랜치 없음?
    - 검증: `git remote -v`로 단일 origin + 환경별 브랜치 없음

[2] 의존성 명시·격리
    - package.json/requirements.txt에 모든 의존성 명시?
    - 시스템 전역 패키지 의존하지 않음?
    - 검증: 깨끗한 디렉토리에서 `npm ci`만으로 실행 가능

[3] 환경변수 분리
    - API key·DB URL이 코드에 하드코딩 안 됨?
    - .env.local과 .env.production 분리?
    - 검증: grep으로 하드코딩된 URL·key 0개

[4] 백업 서비스 어댑터
    - DB·캐시·LLM API·스토리지가 어댑터 패턴으로 추상화?
    - lib/db/index.ts 같은 단일 진입점에서 환경변수 분기?
    - 검증: 직접 SDK 호출 없이 추상화 계층 통과

[5] 빌드/릴리스/실행 분리
    - npm run build로 빌드 산출물 생성 가능?
    - 빌드 산출물 + 환경변수만으로 어디서든 실행 가능?
    - 검증: dist/ 또는 .next/ + .env로만 실행 가능

[6] 무상태 프로세스
    - 세션·캐시가 인메모리에 저장 안 됨?
    - 사용자 데이터는 DB·외부 캐시에 저장?
    - 검증: 모듈 레벨 mutable 상태 grep 0개

[7] 포트 바인딩
    - 앱이 자체적으로 HTTP 서버 노출 (Apache/Nginx 의존 없음)?
    - PORT 환경변수로 포트 변경 가능?
    - 검증: PORT=8080 npm start로 다른 포트 실행 가능

[8] 동시성 (수평 확장 가능)
    - 백그라운드 작업이 별도 프로세스로 분리?
    - setInterval·인메모리 cron 없음?
    - 검증: 코드에 setInterval 같은 인메모리 스케줄러 0개

[9] 빠른 시작·정상 종료
    - 앱이 10초 이내 시작 가능?
    - SIGTERM 시그널로 graceful shutdown?
    - 검증: time npm start 측정 + kill -TERM 정상 종료 확인

[10] 개발-운영 동등성
    - 로컬 DB와 인프라 DB가 호환 가능 (둘 다 SQL)?
    - 외부 API·LLM이 로컬·인프라 동일 엔드포인트?
    - 검증: 로컬 전용 라이브러리만 의존 안 함 (sqlite3만 있고 pg 없으면 FAIL)

[11] 로그를 이벤트 스트림으로
    - 로그가 stdout으로 나감 (파일에 직접 안 씀)?
    - console.log만 씀?
    - 검증: fs.writeFile로 로그 쓰는 부분 0개

[12] 관리 작업 일회성
    - DB 마이그레이션이 일회성 스크립트?
    - 시드 데이터 주입이 일회성?
    - 검증: package.json scripts에 migrate·seed 항목 존재

[13] 서버리스 런타임 호환성
    - Edge Runtime 가정 코드가 Node.js 호환 모드로도 실행?
    - Lambda 콜드스타트 가정해 글로벌 변수에 의존 안 함?
    - 파일시스템 쓰기를 /tmp 외 경로에 안 함?
    - 검증: fs.writeFile 사용 시 모두 /tmp 또는 환경변수 경로
```

**13개 검증 결과 형식:**
```
| # | 항목 | PASS/FAIL | 이슈 |
|---|------|-----------|------|
| 1 | 코드베이스 | PASS | - |
| 2 | 의존성 명시 | PASS | - |
| ... | ... | ... | ... |
```

**FAIL이 1개라도 있으면**: §12 완료 보고에 명시. 플래너 판단으로 (a) Claude Code에게 수정 지시 (b) 그대로 B-2 진입 (그 항목 인지하고 인프라에서 해결).

#### 13. Kill / Go / Hold 판정

A 트랙과 동일.

- **Go** — Claude Code bypass 세션 진입. 근거 3줄.
- **Kill** — 여기서 종료. 근거 3줄. (B-1 단계 Kill은 "A 기획이 아직 빌드 가능한 상태가 아니다"라는 뜻. A-2로 회귀.)
- **Hold** — 특정 외부 확인 후 재판정. 무엇을 확인해야 하는지 명시. 최대 2회.

**B-1 단계 Hold이 흔한 이유:**
- 섹션 3 기술 리스크 조사 결과 중 Hold 플래그 (예: 만세력 검증)
- 섹션 1 체크리스트에 플래너가 아직 준비 안 한 계정
- 섹션 7 결정 항목에 플래너가 아직 답 안 함

이 셋 중 하나라도 미해결이면 Go 불가. Hold.

## B-1 산출물에서 흔한 실패 모드

**실패 1: 기술 스택에 SaaS 포함**
- 예: §2에 Supabase·Vercel
- 왜 나쁜가: B-1은 로컬 한정. SaaS는 B-2 영역
- 교정: 로컬 도구로 교체 (SQLite, 로컬 실행)

**실패 2: 사전 조사가 층위 3로 감 (깊이 초과)**
- 예: 라이브러리 3개를 실제 설치해서 10개 샘플 돌림
- 왜 나쁜가: B-1 작성에 1시간 넘게 쓰면 비용 대비 가치 감소
- 교정: 층위 2 기본. 층위 3 승격은 "검증 축 직결 + Hold 불가피" 두 조건 모두 만족 시만

**실패 3: 플래너 결정 항목이 "초안 떠넘기기" 패턴**
- 예: `[SO 결정 필요] 만세력 어느 거 쓰죠?` (옵션·추천 없이)
- 왜 나쁜가: 정책 v15 원칙 5 위반
- 교정: 옵션 2~4개 + Claude 추천 + 이유 필수

**실패 4: Claude Code 재량 범위가 불명확**
- 예: "자잘한 건 알아서"
- 왜 나쁜가: 실제 bypass에서 Claude Code가 여전히 물어봄
- 교정: 행동 규칙 목록 형태로 구체화

**실패 5: 멈춤 트리거가 추상적**
- 예: "위험한 일 하면 멈춤"
- 왜 나쁜가: Claude Code가 "위험"을 판정 못 함 → 안 멈춤
- 교정: 구체적 행동 4가지로

**실패 6: 재시도 상한 누락**
- 왜 나쁜가: 같은 실패 30번 반복하며 플래너 호출 안 함
- 교정: §9.5 디폴트 3개 룰 박기

**실패 7: 검증 방법이 "작동함" 수준**
- 왜 나쁜가: Claude Code가 "통과"를 선언해도 실제 통과 판정 불가
- 교정: A-1 §4 시나리오 기반 + PASS 조건 구체 관찰 항목 3~5개

**실패 8: 포터빌리티 13개 체크 누락 또는 표면적 검증**
- 예: "PASS"라고만 적고 실제 검증 명령 안 실행
- 왜 나쁜가: B-2에서 인프라 올릴 때 구조 변경 필요 → 분리 의미 상실
- 교정: 각 항목에 실제 검증 명령 명시 (grep·time·실행 명령 등)

**실패 9: 환경변수 추상화 미흡**
- 예: API 호출 코드에 `https://api.anthropic.com` 하드코딩
- 왜 나쁜가: 12-Factor [3] 환경변수 분리 위반. B-2 전환 시 코드 수정
- 교정: 모든 외부 의존을 환경변수로

## B-2 진입 조건 (Go 판정 시)

B-1이 Go로 끝나면 B-2 진입 가능. **다음 셋 모두 만족 시만:**

1. **B-1 산출물 파일이 저장됨** (`04_B-1_로컬에서만들기_[프로젝트명].md`)
2. **Claude Code 빌드 완료** (시나리오 PASS + 13개 체크 결과)
3. **§12 완료 보고가 작성됨** (B-2 입력으로 사용)

이 셋 중 하나라도 미충족이면 B-2 진입 불가.

**13개 체크 FAIL 항목 처리:**
- 모두 PASS → 즉시 B-2 진입 가능
- FAIL 1~3개 → 플래너가 영향 분석 후 결정 (수정 지시 또는 그대로 B-2)
- FAIL 4개 이상 → B-1으로 회귀 권장 (포터빌리티가 너무 깨져 있음)

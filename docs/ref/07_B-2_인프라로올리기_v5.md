# 07 B-2 인프라로올리기 v5

> 00 기획 하네스 정책 v15을 토대로 한다. 작성 전 정책 문서의 "안 읽힘 6원인"·"문장 원칙"·"AI의 역할"·"번들링"·"변경 가시화"·"턴 카운팅"을 참조한다.

---

## 이 문서 사용법

B-2는 **하네스의 다섯 번째이자 마지막 핵심 문서**이다. B-1에서 로컬 검증을 통과한 MVP를 **인프라(Vercel·Supabase 등 SaaS)로 안전하게 배포**하는 단계.

**B-2의 정체성: 안전한 인프라 배포.**

플래너의 핵심 우려: "MVP라도 해당 인프라는 서비스에 이미 쓰고 있으면 서비스 인프라에 영향을 줄까봐 무섭다." 이게 B-2 워크플로우의 출발점이다.

따라서 B-2는 **read-first 패턴**으로 동작한다:
1. 매 단계 시작 전 **기존 인프라 상태 read**
2. read 결과를 `현재인프라_[프로젝트명]_[날짜].md`로 저장 (또는 갱신)
3. AI가 변경 제안 + 영향 분석 + 사용자 확인
4. 사용자 승인 후 **단계별 진행** (단계 끝나면 다시 read해서 갱신)

**B-1과의 분리:**
- B-1: 로컬 실행 + 시나리오 PASS + 포터빌리티 13개 검증
- B-2: B-1 결과물을 인프라에 배포 (별개 산출물)

이 문서에는 두 가지가 같이 들어 있다:
1. **산출물 템플릿** — B-2 산출물이 최종적으로 어떤 형태여야 하는가
2. **워크플로우** — Claude와 플래너가 어떤 순서로 채워가는가

Claude는 이 문서와 기획 하네스 정책 v15을 함께 읽은 뒤 B-2 산출물 작성을 시작한다.

B-1의 산출물(완료 보고: 시나리오 PASS + 13개 체크 결과)과 A-0·A-1·A-2 산출물이 B-2의 입력이다. B-1 없이 B-2 진입 불가.

B-2 산출물이 Go로 끝나면 Claude Code가 인프라 배포 단계를 실행한다. 단 **사용자 단계별 확인 모드** — 모든 결정 지점에서 AI 제안 + 영향 분석 후 사용자 승인 필요.

## B-2 단계의 정체성

**함의 1. 단계별 자동 (해석 Y).**
B-1은 결정 후 자동 실행이었다. B-2는 다르다. 인프라는 결제·과금·외부 노출·기존 서비스 영향 같은 비가역 작업이 섞여 있어 100% bypass 위험. **모든 단계에서 사용자 확인.**

플래너 명시:
> "AI가 직접해도 하나 하나 왜 그걸하는지 설명하고 뭘 할지 제안한 후에 사용자가 선택하면 진행. 모두 자동화고 사용자는 선택만."

이게 v1의 디폴트. 실전 후 점진적으로 사용자 확인 단계 줄여 v2에서 X(결정 단위 자동)로 전환 가능.

**함의 2. read-first 워크플로우.**
플래너 명시:
> "인프라 배포 전에 read 기능으로 기존 서비스 뭐가 있고 이런거 분석해서 md로 만들고, 다음 들어갈때 그 md 보고, 다시 다 read해서 업데이트해서 진행하고 해야 한다고 생각함."

이게 핵심 안전 장치다. **매 단계 시작 전 read → 현재 상태 갱신 → 변경 제안.**

**함의 3. 1차 독자는 Claude Code.**
B-1과 동일. 플래너는 §1·§7·§11·§12만 직접 읽음. 나머지는 Claude Code가 읽고 실행.

> - **이 문서 (템플릿+워크플로우)**: 분량 제한 없음. 작성 가이드다.

### 산출물 구조

B-2 산출물의 최종 형태는 아래 9개 섹션으로 구성된다.

```
[맨 앞] 1차 독자 선언문 (1차 독자는 Claude Code, 플래너는 §1·§7·§11·§12만 읽음)

0. B-1 완료 보고 + A 트랙 핵심 요약
1. 시작 전 체크리스트 (인프라 서비스 계정·결제 수단)
2. 인프라 서비스 결정 (DB·배포·모니터링)
3. 마이그레이션 계획 (로컬 DB → 인프라 DB)
4. 환경변수 마이그레이션 (.env.local → 배포 환경변수)

6. 롤백 계획 (배포 실패 시)
7. 비용 모니터링 (무료 티어 한도 + 결제 한도)
8. [SO 결정 필요] 항목
9. Kill / Go / Hold 판정

[맨 끝] Claude의 적대적 압박 — "Kill할 이유 세 가지"
```

### 섹션별 상세

#### 0. B-1 완료 보고 + A 트랙 핵심 요약

B-1·A-2·A-1·A-0의 핵심을 맨 앞에 고정. Claude Code가 인프라 배포 중에 "지금 뭘 배포하고 있는 거였지"를 잊지 않도록.

- **B-1 완료 보고 핵심**: 시나리오 PASS 결과 + 13개 체크 결과 (FAIL 항목 있으면 명시)
- **A-0 핵심 가설 한 문장**
- **A-1 Phase 구조 개요**
- **A-2 화면 목록**
- **MVP 경계 3개**

#### 1. 시작 전 체크리스트

**플래너가 B-2 시작 전에 반드시 완료해둬야 할 것.** 인프라 서비스 영역.

체크박스 형식:
```
[ ] <서비스> 계정 생성 + 결제 수단 등록
    → 필요한 것: <구체 정보>
    → 발급/등록 위치: <URL>
[ ] <도메인> 결정 (있으면)
    → 도메인 이름: <이름>
    → 등록 기관: <어디>
```

**필수 포함 카테고리:**
- 배포 서비스 (Vercel·Netlify·Cloudflare 등) — 무료 티어 가입 + 결제 정보 (한도 설정)
- DB 서비스 (Supabase·Neon·PlanetScale 등) — 무료 티어 가입
- 도메인 (선택사항) — 보통 MVP 단계엔 SaaS 무료 도메인 사용
- 모니터링 (Vercel Analytics·Sentry 등, 선택사항)

**중요: 결제 한도 설정**
무료 티어 초과 시 자동 결제 막기 위해 각 서비스에서 spending limit 설정 강제. AI가 빌드 중에 의도치 않은 비용 발생 방지.

**좋은 예시:**
```
[ ] Vercel 계정 + 무료 Hobby 티어 가입 (vercel.com)
    → 결제 한도 설정: 월 $5 (안전 마진)
    → GitHub repo 연결 권한 부여
```

**나쁜 예시:**
```
[ ] 배포 서비스 가입
```

#### 2. 인프라 서비스 결정

**Claude가 옵션 + 추천 + 이유 제시 → 플래너 선택 → AI 자동 실행**

각 카테고리마다 결정. AI가 일방 결정 금지. 정책 v15 원칙 5 적용.

**결정 카테고리:**
- 배포 서비스
- DB 서비스
- 모니터링 도구 (선택사항)
- CDN·이미지 호스팅 (필요 시)
- 백그라운드 작업 처리 (필요 시)

**B-2 결정 원칙:**
1. **기존 서비스 영향 최소화** — 플래너가 이미 운영 중인 서비스가 같은 인프라에 있으면 분리된 프로젝트·계정·DB 사용
2. **무료 티어 우선** — MVP 단계 비용 0 가능한 옵션
3. **B-1 어댑터와 호환** — 코드 변경 없이 환경변수만으로 전환 가능한 서비스

**좋은 예시 (사주톡 DB 결정):**
```
[결정] DB 서비스

옵션:
- A: Supabase (Postgres + Auth + Realtime)
  + 통합 솔루션, Auth 무료
  + Drizzle 호환
  - 기존에 이미 다른 프로젝트로 쓰고 있다면 분리 필요
  - Vendor lock-in 약간

- B: Neon (Postgres only, 서버리스)
  + 순수 Postgres, 어댑터 그대로
  + 더 가벼움
  - Auth 별도 필요

- C: PlanetScale (MySQL)
  + Branching DB
  - MySQL이라 코드 일부 수정 필요 (B-1이 Postgres 호환이면)

Claude 추천: A (Supabase)
이유:
1. B-1 Drizzle 어댑터가 그대로 작동
2. Auth까지 무료 티어로 해결 (사주톡 추후 회원 기능 확장 대비)
3. 기존 사용 중이면 새 프로젝트로 분리 (DB·이름스페이스 격리)

기존 서비스 영향 분석:
- 플래너 명시 시: 기존 Supabase 사용 중 → 새 프로젝트로 분리. 이름: sajutalk-prod
- 기존 사용 없음 → 새 계정으로 시작
```

**나쁜 예시:**
```
DB는 Supabase 씁니다.
```
이유: 옵션·이유 없음. 영향 분석 없음. 사용자 선택권 박탈.

#### 3. 마이그레이션 계획 (로컬 DB → 인프라 DB)

**B-1의 로컬 DB 스키마·데이터를 인프라 DB로 이전하는 단계별 계획.**

read-first 원칙 적용:
1. **인프라 DB 현재 상태 read** — 기존 테이블·schema·data 확인
2. **로컬 DB 상태 read** — 마이그레이션 대상 확인
3. **충돌 분석** — 인프라에 이미 같은 이름 테이블 있는지
4. **마이그레이션 SQL 생성** — 사용자 확인 후 실행

**좋은 예시:**
```
[마이그레이션 단계]
1. read: 인프라 DB 현재 schema 스캔 (`\dt` in psql)
   → 결과 저장: 현재인프라_[프로젝트명]_[날짜].md

2. 충돌 검사: B-1 schema와 인프라 schema 비교
   → AI 제안: "기존 테이블 X와 충돌 없음. 안전하게 추가 가능."
   → 사용자 확인: [예/아니오]

3. 마이그레이션 SQL 생성 (Drizzle migrate)
   → AI 제안: "다음 SQL 실행 예정: [SQL]"
   → 사용자 확인: [예/아니오/수정]

4. SQL 실행 (사용자 승인 후)

5. 검증: 인프라 DB에서 schema 다시 read → 의도한 대로 적용됐는지
   → 결과 저장: 현재인프라_[프로젝트명]_[날짜].md (갱신)
```

**나쁜 예시:**
```
인프라 DB에 schema 적용.
```
이유: read 없음. 충돌 검사 없음. 사용자 확인 없음.

#### 4. 환경변수 마이그레이션

**.env.local의 모든 값을 인프라 환경변수로 이전.**

**원칙:**
- 코드 수정 0 — B-1에서 12-Factor 원칙 지켰으면 환경변수 값만 바꾸면 됨
- 비밀 키 안전 처리 — 인프라 대시보드에 직접 입력, 코드 커밋 금지

**좋은 예시:**
```
| 변수 | 로컬 값 | 인프라 값 | 위치 |
|------|---------|-----------|------|
| ANTHROPIC_API_KEY | sk-... (개인) | sk-... (프로덕션 키 별도) | Vercel env |
| DATABASE_URL | sqlite:./data/saju.db | postgresql://... (Supabase) | Vercel env |
| DATABASE_PROVIDER | sqlite | postgres | Vercel env |
| NODE_ENV | development | production | Vercel env (자동) |
```

**중요 — API key 분리:**
로컬 개발용 key와 프로덕션 key는 분리. 로컬 key가 유출돼도 프로덕션 영향 없게.

#### 5. 배포 순서

**의존성 있는 순서대로 단계 나열.**

read-first + 사용자 확인 패턴:

```
[단계 N: 단계 이름]

1. read: 현재 상태 확인 (`현재인프라_[프로젝트명]_[날짜].md` 갱신)
2. AI 제안: 다음 작업 X를 실행할 예정
3. 영향 분석: 이 작업이 기존에 미치는 영향
4. 사용자 확인: [예/아니오]
5. 실행 (사용자 승인 후)
6. 검증: 기대한 결과 나왔는지
7. 다음 단계로
```

**좋은 예시 (사주톡):**
```
1. GitHub 저장소 push (B-1 완료 코드)
   - read: GitHub 현재 상태
   - 제안: 새 repo 생성 + push
   - 확인: [예]
   - 실행

2. Vercel 프로젝트 생성 + GitHub 연결
   - read: Vercel 기존 프로젝트 목록
   - 제안: 새 프로젝트 sajutalk 생성, github repo 연결
   - 영향: 기존 프로젝트 영향 없음
   - 확인: [예]
   - 실행

3. Supabase 프로젝트 생성
   - read: Supabase 기존 프로젝트 목록
   - 제안: 새 프로젝트 sajutalk-prod 생성 (기존과 분리)
   - 영향: 기존 프로젝트 0
   - 확인: [예]
   - 실행

4. DB 마이그레이션 (§3 계획대로)
   - 단계별 진행

5. 환경변수 설정 (§4 표대로)
   - read: Vercel 환경변수 현재 상태
   - 제안: 다음 변수 추가
   - 확인: [예]
   - 실행

6. 첫 배포 트리거 (Vercel)
   - read: 배포 빌드 로그
   - 제안: 빌드 시작
   - 확인: [예]
   - 실행 (자동)
   - 검증: 빌드 성공 + URL 응답 확인

7. 배포 URL에서 시나리오 1·2 검증
   - 수동 또는 자동
   - 결과 기록

8. 도메인 연결 (선택사항)
   - 사용자 결정

9. 모니터링 셋업 (선택사항)
   - Vercel Analytics 활성화 등

10. §12 완료 보고 생성
```

각 단계는 read → 제안 → 확인 → 실행 → 검증 사이클. **사용자 확인 없이 다음 단계로 가지 않음.**

#### 6. 롤백 계획

**배포 실패 시 안전하게 되돌리는 계획.** B-1엔 없던 신규 섹션.

**롤백 트리거:**
- 배포 후 시나리오 1·2 PASS 안 됨
- 기존 서비스에 의도치 않은 영향 발생
- 비용이 예상치 초과

**롤백 단계 (디폴트):**
1. **트래픽 차단** — Vercel 배포 비활성화 (DNS는 유지하되 maintenance mode)
2. **DB 스냅샷** — 변경 전 상태로 복구 (Supabase point-in-time recovery 등)
3. **환경변수 되돌리기** — 이전 값으로 (인프라 대시보드에서)
4. **GitHub 이전 커밋으로 redeploy** — 또는 배포 자체 삭제

**좋은 예시:**
```
[롤백 시나리오 1] 배포 후 시나리오 FAIL
- 트리거: 시나리오 1 또는 2 FAIL
- 단계:
  1. Vercel 배포 비활성화 (즉시)
  2. 원인 분석: 로그 read
  3. 수정 가능 → B-2 §5 단계 N으로 회귀, 수정 후 재배포
  4. 수정 불가 → B-1로 회귀

[롤백 시나리오 2] 비용 한도 초과 알림
- 트리거: Vercel 또는 Supabase에서 한도 초과 알림
- 단계:
  1. 즉시 Vercel 배포 비활성화
  2. 사용량 분석: 어느 API가 폭주했는지
  3. 원인 수정 (예: rate limiting 추가)
  4. 한도 재설정 후 재배포
```

#### 7. 비용 모니터링

**무료 티어 한도 + 결제 한도 명시.**

**플래너 직접 읽는 섹션 (§7).** Claude Code 참조도 됨.

**좋은 예시:**
```
| 서비스 | 무료 티어 한도 | 결제 한도 (안전 마진) | 모니터링 방법 |
|--------|---------------|---------------------|---------------|
| Vercel | 100 GB-hr/월 | 월 $5 | Dashboard usage |
| Supabase | 500MB DB, 50K MAU | 월 $0 (Free tier 강제) | Dashboard usage |
| Anthropic API | - | 월 $20 (충전 한도) | Console usage |

총 예상 월 비용: $0 ~ $25 (LLM API 사용량에 따라)
```

**알림 설정:**
- 각 서비스에서 한도의 80% 도달 시 이메일 알림 활성화
- 100% 도달 시 자동 정지 (가능한 경우)

#### 8. [SO 결정 필요] 항목

정책 v15 원칙 5 적용. 옵션 + 추천 + 이유 필수.

**B-2에서 흔한 결정 항목:**
- 도메인 사용 여부 (무료 SaaS 도메인 vs 구입한 도메인)
- 모니터링 깊이 (기본 Analytics만 vs Sentry 추가)
- DB 백업 빈도
- 환경별 설정 (staging 환경 만들지 vs production 직행)

**형식:**
```
[SO 결정 필요] N: [한 줄 질문]
- 옵션 A: [구체 안] — 장단점
- 옵션 B: [구체 안] — 장단점
- Claude 추천: [A 또는 B]
- 이유: [핵심 가설 또는 MVP 경계와 연결]
```

#### 9. Kill / Go / Hold 판정

A 트랙·B-1과 동일.

- **Go** — Claude Code 인프라 배포 세션 진입. 근거 3줄.
- **Kill** — 여기서 종료. 근거 3줄. (B-2 단계 Kill은 "B-1 결과물이 인프라로 못 올라간다" 또는 "비용·기존 서비스 영향이 너무 크다"라는 뜻.)
- **Hold** — 특정 외부 확인 후 재판정. 무엇을 확인해야 하는지 명시. 최대 2회.

**B-2 단계 Hold이 흔한 이유:**
- 섹션 1 체크리스트에 플래너가 아직 준비 안 한 결제 수단·계정
- 섹션 2 인프라 서비스 결정에 플래너가 아직 답 안 함
- 기존 서비스 영향 분석 불충분
- B-1 13개 체크에 FAIL 4개 이상 → B-1 회귀 필요

## B-2 산출물에서 흔한 실패 모드

**실패 1: 기존 인프라 영향 분석 누락**
- 예: "Supabase 새 프로젝트 만듭니다"라고만 적고 기존 사용 영향 안 봄
- 왜 나쁜가: 같은 계정 다른 프로젝트가 quota 영향받을 수 있음
- 교정: 매 단계 read-first + 영향 분석 명시

**실패 2: 롤백 계획 부재 또는 표면적**
- 예: "실패하면 되돌립니다"
- 왜 나쁜가: 어떻게 되돌리는지 불명확. DB 마이그레이션 실패 시 데이터 손실 가능
- 교정: 시나리오별 구체 단계 + DB 스냅샷 명시

**실패 3: 비용 한도 미설정**
- 예: 무료 티어만 명시하고 결제 한도 안 박음
- 왜 나쁜가: LLM API 폭주 시 한 달 수백 달러 발생
- 교정: 모든 서비스에 결제 한도 + 알림 설정 의무

**실패 4: 환경변수 로컬·인프라 혼동**
- 예: 로컬 API key가 인프라에 그대로 적용
- 왜 나쁜가: 로컬 key 유출 시 프로덕션 영향
- 교정: 프로덕션 key 별도 발급 명시

**실패 5: 단계별 사용자 확인 무시**
- 예: AI가 자동으로 다음 단계 진행
- 왜 나쁜가: 비가역 작업이라 사용자 확인 필수
- 교정: 매 단계 명시적 [예/아니오] 확인

**실패 6: read-first 워크플로우 무시**
- 예: 기존 상태 모르는 채로 변경 진행
- 왜 나쁜가: 기존 서비스 충돌 가능
- 교정: 매 단계 시작 시 read → 현재 상태 갱신 강제

**실패 7: 배포 후 검증 누락**
- 예: 배포 URL 받고 끝
- 왜 나쁜가: 시나리오 PASS 확인 없이 완료 선언
- 교정: 배포 URL에서 시나리오 1·2 PASS 의무
